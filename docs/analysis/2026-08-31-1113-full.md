## 3. Stability — B+ (Solid)

### What was measured

Every claim below comes from source at a named line, from a command's output,
or from a measured number. Section 9 reproduces all of it.

**Crash surface.** Exactly one `std::abort()` exists in the tree
([`core/src/assert.cpp:16`](../../packages/core/src/assert.cpp)), reached only
through `ENGINE_ASSERT` / `ENGINE_ASSERT_MSG`. There is no `throw`, no
`std::exit`, no `std::terminate` call anywhere in `packages/` outside comments.
77 assert sites: 55 in `rhi-d3d12`, 12 in `core`, 9 in `scene`, 1 in
`renderer`.

**Asserts are live in Release.** `assert.hpp` has no `NDEBUG` guard, and this
is deliberate and documented at
[`docs/FOUNDATION.md:44`](../FOUNDATION.md): asserts "live in **both** Debug
and Release … Reserve them for genuine programmer error … Capacity that depends
on content (arena, frame ring, descriptor window) returns a failure instead,
because aborting there is unrecoverable *and* untestable: no gate can exercise
a path that calls `std::abort()`."

**The policy is honoured, not just stated.** I traced every content-reachable
capacity to see whether it asserts or degrades:

| Capacity | Cap | At the limit |
|---|---|---|
| Scene instances | 512 | `scene_file.cpp:276` and `prefab.cpp:128` **bound-check before** calling `add_instance`, and return `false` / `kInvalidInstance` |
| Scene materials | 16 | `scene_file.cpp:260` bound-checks before `add_material` |
| Physics bodies | 256 | `physics_cpu.cpp:663` logs `"Physics: body pool full"`, returns an invalid handle |
| Frame arena | per-frame | logs `"Frame arena exhausted: 512 bytes used of 1024, 4096 more requested. Work is being dropped this frame."` — observed live in the gate run |
| Frame constant ring | 1 MiB/slot | drops draws, does not abort; `Frame ring budget gate` reports 42.6% headroom |
| Shader descriptors | 8192/frame | `device_d3d12.cpp:1179` logs once and reuses the last slot rather than aborting, with the reasoning in-place |
| Physics contact / trigger buffers | 512 / 256 | `warn_physics_capacity`, one latch **per kind** (`physics_cpu.cpp:409`) |
| Profiler scope table | 8 | warns once, `physics_cpu`-style latch, at `profile.cpp` `accumulate()` |

So the nine `scene` asserts that look like content-reachable aborts are all
preceded by an explicit bound check on the only paths that reach them from a
file. That kills the obvious finding.

**Untrusted-input parsing is careful.** `assets/src/pak.cpp` uses a
bounds-checked `Cursor`, rejects names containing `..`, `\`, NUL or control
characters, rejects duplicates via a `std::unordered_set`, and validates the
offset chain in `u64` so a crafted 32-bit offset cannot wrap. glTF loading
refuses accessor, view and index overruns — three rejections observed live in
the gate output (`glTF failed validation (cgltf_result 1) — refusing to load`).
Mount containment blocks `..`, absolute paths, UNC paths and rooted paths, all
four observed live.

**Device loss is handled.** `engine.cpp:311` checks `device_->device_lost()`
every frame, logs Fatal with a message that distinguishes a driver reset from a
content error, exits the loop and calls `wait_idle()`. `device_d3d12.cpp:2489`
latches on `DXGI_ERROR_DEVICE_REMOVED` / `_RESET` from `Present`, and
`DXGI_STATUS_OCCLUDED` is handled separately. The resize path
(`device_d3d12.cpp:1388`) waits for the GPU, re-checks removal after the wait,
resets command-list resource refs, and **recovers to the old dimensions** if
`ResizeBuffers` fails.

**NaN discipline.** `Mat4::perspective` clamps three unguarded denominators
(`mat4.cpp:47`), with the observed failure written at the site. `inv_mass_of`
handles NaN mass explicitly, and the comment records the full causal chain that
motivated it: NaN mass → NaN velocity → NaN AABB → every overlap comparison
false → "the body silently vanished from the broadphase and shipped a NaN model
matrix to the GPU". The `Math guard gate` asserts all four cases.

### Findings

**S1 — Medium. `end_copy()` submits a command list whose `Close()` failure it
never checks.**

`packages/rhi-d3d12/src/device_d3d12.cpp:1756`:

```cpp
UINT64 D3D12Device::end_copy() {
    copy_list_->Close();
    ID3D12CommandList* lists[] = {copy_list_.get()};
    queue_->ExecuteCommandLists(1, lists);
```

450 lines earlier, the frame path does check it — line 1307 — and the comment
above it says the check "is the difference between a logged bad frame and a
driver fault". `ExecuteCommandLists` on a list whose `Close()` failed is
undefined and typically removes the device. `begin_copy()` (line 1751) likewise
discards `copy_allocator_->Reset()` and `copy_list_->Reset()`.

*Failure scenario:* an invalid `CopyTextureRegion` or `CopyBufferRegion`
recorded on the copy list — bad footprint, mismatched subresource — puts the
list in an error state; `Close()` returns a failure HRESULT that nobody reads;
the list is submitted; the device is removed. The engine then reports "GPU
device lost … a driver reset, a TDR, or a removed adapter, **not a content
error**" — which would be exactly wrong.

*Why it survived Pass 4:* I checked whether the copy arguments are all
engine-computed and therefore safe. They are computed via
`GetCopyableFootprints` and guarded by asserts on mip count and array size
(lines 1845–1849), so I cannot name content that reaches an invalid copy
today — which is why this is Medium and not High. But the asymmetry is
undocumented, the fix is the same three lines that already exist upstream, and
no gate covers the copy path's failure mode.

**S2 — Medium. A null pipeline pointer silently disables a render pass.**

Every `should_execute` predicate in
`packages/renderer/src/standard_frame.cpp` treats a null pipeline as "feature
off" with no log:

```cpp
velocity.should_execute = [](const RenderSnapshot& snapshot) {
    return snapshot.motion_pipeline != nullptr;      // line 112
};
```

Sixteen such predicates. A pipeline pointer reaches the snapshot through three
hand-written copy blocks across four structs (`ForwardDemo` →
`WorldExtractAssets` → `ExtractDesc` → `RenderSnapshot`), so a forgotten copy
line produces a pass that never runs and never complains. This is named
explicitly in
[`.claude/rules/renderer-boundaries.md`](../../.claude/rules/renderer-boundaries.md)
("Missing a step fails **silently**"), and each shipped feature has a gate that
asserts its pass is present (`Motion gate: … pass=yes`). So the class is
covered by convention plus a checklist plus per-feature gates — but nothing logs
at graph-compile time, so the *next* pass added is protected only by whoever
remembers step 6.

**S3 — Low. Profiler scope stack goes out of balance past depth 8.**

`begin_scope` drops the push when `depth_ >= kMaxScopes` but `end_scope` still
decrements, so past depth 8 the elapsed time is attributed to a scope that is
still open and the imbalance cascades. The defect is documented in place at
`packages/core/src/profile.cpp` with the correct fix named ("count dropped
pushes and skip the matching pops") and correctly assessed as unreachable:
deepest actual nesting is 3, and I confirmed **7 distinct scope names** exist
against 8 slots (`frame`, `poll_events`, `fixed_update`, `update`, `render`,
`extract`, `execute`).

**S4 — Low. No log file sink.** `StdoutLogger::log`
(`core/src/log.cpp:38`) writes to `stderr` and nothing else; there is no other
`ILogger` implementation in the tree. A crash, an assert or a Fatal in a shipped
`game.exe` leaves nothing on disk. Already a Ready row (`ENGINE_MAP.md:58`,
Foundation #6 — "File logger (not only stderr)").

**S5 — Low. Bare asserts abort without a log line.** `assert_fail` calls
`log(LogLevel::Fatal, msg)` **only** when `msg` is non-null, so the ~40 sites
using `ENGINE_ASSERT(expr)` rather than `ENGINE_ASSERT_MSG` abort with output on
`stderr` alone. Combined with S4, the reason is unrecoverable after the fact.

### External comparison

**Unreal Engine's assert policy** is the direct counterpart, and it makes the
opposite choice. Epic's own documentation states the `check` family "do not run
in shipping builds by default", that `DO_CHECK` disables them, and that
"projects should ship with `USE_CHECKS_IN_SHIPPING` set to its default value of
0". Unreal also provides a middle tier Sol lacks entirely: `ensure()`, a
*non-fatal* assert that "will inform the crash reporter, but will continue
running" and reports once per session.

Where this tree differs, and whether it is a deficiency or a trade:

- **Always-on asserts: a deliberate trade, defensible.** Unreal compiles away
  the same class of violated precondition in the build players actually run.
  Sol keeps them, which converts a silent-wrong-state bug into a visible abort.
  That is only defensible because the discipline about *where* asserts may live
  is real — and I verified it is, at every content-reachable site.
- **No `ensure()` tier: a deficiency.** Unreal's non-fatal, report-once assert
  is what makes always-on checking survivable in shipping. Sol has fatal or
  nothing.
- **No crash reporter and no log file: a deficiency.** Unreal's `ensure` routes
  to a crash reporter; Sol's abort routes to a console window that closes with
  the process.

### What is genuinely good here

The comment discipline is the strongest thing in this dimension and it is not a
documentation nicety — it is post-mortem evidence embedded at the site of the
fix. `inv_mass_of` records the exact causal chain of a NaN. `warn_physics_capacity`
records why one shared latch was wrong ("the first kind to trip permanently
silenced the others"). `next_shader_descriptor` records why exhaustion reuses a
slot rather than aborting ("a terminated process is neither recoverable nor
debuggable on a player's machine"). `profile.cpp` records both things
`kMaxScopes` bounds and which one is near its limit. A reader can reconstruct
the failure history of this engine from its comments alone.

## 4. Architecture — A− (Exemplary)

### What was measured

**The graph.** 26 packages, 49 edges, extracted from every
`packages/*/CMakeLists.txt`:

```
core          -> (none)
math          -> core
platform      -> core          rhi     -> core        shaders -> core
assets        -> core math     audio   -> core math   physics -> core math
platform-win32-> platform      rhi-d3d12 -> math rhi   shaders-dxc -> shaders
audio-xaudio2 -> audio         physics-cpu -> physics
assets-filesystem -> assets platform    assets-gltf -> assets
assets-obj    -> assets        assets-gpu -> assets rhi   assets-png-wic -> assets
renderer      -> core math rhi
debug-draw    -> core math rhi shaders
scene         -> assets core math
gameplay      -> core math physics
engine        -> assets audio core physics platform renderer rhi
cook          -> assets assets-gltf assets-obj assets-png-wic core math
sandbox, game -> via engine_add_runtime_app
```

Three properties hold, and each is machine-checked:

1. **`renderer` depends on `{core, math, rhi}` and nothing else.** No `scene`,
   no `assets`, no `debug-draw`, no graphics API. Checked two ways — the
   dependency-direction invariant, and a dedicated `renderer-scene-isolation`
   check that greps for `#include <engine/scene/`.
2. **No backend is reachable from any non-app package.** Every `*-win32`,
   `*-d3d12`, `*-dxc`, `*-xaudio2`, `physics-cpu`, `assets-*` appears only in
   the two app targets' link lists. `gameplay` depends on `physics`, the
   interface — not `physics-cpu`. `engine` depends on interfaces plus
   `renderer`, no implementations.
3. **The layer table refuses to be bypassed.** Layers are hardcoded in
   `tools/check-invariants.ps1` with ranks finer than the four named layers, and
   an unlisted package **fails** the run rather than being skipped. Adding a
   package is therefore forced to be an explicit architectural decision.

**Deletability test, actually performed.** Delete `debug-draw`: the render graph
calls overlay and line drawing through `std::function` members on
`StandardFrameDesc` (`standard_frame.cpp:323, 340`), so `renderer` does not
link it and nothing in the engine breaks — only the two app targets, which
reference three headers. Delete `physics-cpu`: `gameplay` is unaffected because
it depends on `physics`; only the apps' `ENGINE_HAS_PHYSICS_CPU` block breaks,
and that block is already `if(TARGET …)`-guarded in CMake. Both seams are real.

**Interface-with-one-implementation check.** `shaders` is 64 lines with two
headers and one backend — the smell the standard warns about. It is not
over-engineering: `ShaderTarget` already has `Spirv`, the DXC backend
explicitly rejects it with a logged error, and the `RHI contract gate` asserts
`spirv_rejected=yes`. The second buyer is named in code and tested. Same for
`physics` (97 lines) and `platform` (301).

### Findings

**A1 — Medium. The layering stops at the app boundary, and the player binary
is the test harness.**

`packages/sandbox/src/main.cpp` is **5,708 lines** containing all 67 gate
functions. `cmake/EngineRuntimeApp.cmake:20` builds *both* `sandbox.exe` and
`game.exe` from that same file; `game` is the same source with
`ENGINE_GAME_APP` defined, an icon, and `content.pak`. Measured: the Release
`build/bin/Release/game.exe` contains **82 occurrences of the string `"gate:"`**.
So the engine is 26 carefully separated packages and the application on top of
it is one monolith, shipped as the player.

**A2 — Medium. One render pass costs eight files across two packages, and a
miss fails silently.**

From `.claude/rules/renderer-boundaries.md`, verified against the tree: shader
(1), pipeline constant + desc + create block in `main.cpp` (2), the
`I<Thing>Pipeline*` field added to **four** structs across four files plus three
hand-written copy blocks (3–6), `add_pass` registration in
`standard_frame.cpp` (7), recorder declared in `render_snapshot.hpp` and defined
in `render_graph.cpp` (8), gate. The plumbing is manual pointer copying between
four structurally identical structs, and per S2 a missed copy disables the pass
with no diagnostic.

**A3 — Low. A package does not declare its own layer.** The authoritative layer
mapping lives in a PowerShell script, not next to the package it describes. It
is enforced — an unlisted package fails the check — so this is a locality
observation rather than a correctness one.

### External comparison

**Godot 4 reached this exact design, but by retrofit.** Godot's own rendering
write-up describes the problem: preparing the D3D12 driver revealed "a
significant amount of code needed to be shared between the Vulkan and D3D12
implementations of RenderingDevice", so RenderingDevice was split into "an
API-agnostic layer that contains all the shared code" and "a thin layer that
only includes API-specific code (the RenderingDeviceDriver)", which "has allowed
thousands of lines of duplicate code to be saved". That is structurally the
`renderer` / `rhi` / `rhi-d3d12` split Sol has had from its first backend, and
which a CI check enforces on every push.

Where this tree differs:

- **Advantage, and it is the specific transferable thing.** A reference
  implementation paid for this split in retrofit cost and said so publicly. Sol
  pays for it up front and machine-checks it, so it cannot erode between
  sessions. That is what an Exemplary band requires me to name, and it is real
  independent of whether a second backend exists yet.
- **Deficiency: unvalidated.** Godot's split is proven by three drivers
  (Vulkan, D3D12, and a native Metal backend added in 4.4). Sol's is proven by
  one. Every claim I made about it — new package not rewrite, removable systems,
  API never leaking upward — is a claim about a counterfactual.
- **Scale, for calibration.** `sokol_gfx.h` is "a little over 25,000 lines" for
  five to six backends. Sol's `rhi` interface is 459 lines; `rhi-d3d12` is 2,976.
  The interface is thin because it serves one backend; that is the cost side of
  the same untested-seam observation.

### What is genuinely good here

`tools/check-invariants.ps1` is the mechanism that makes the architecture a fact
rather than an aspiration, and it is unusual enough to be worth stating plainly:
519 lines, eleven checks, no compiler and no GPU, each check carrying a comment
naming the specific past failure it prevents. It is the reason CI is meaningful
in a repository whose real test suite (`--gates`) cannot run on a hosted runner
at all.

## 5. Capabilities — C+ (Working)

### What exists, read from code

**Rendering.** D3D12 backend with compute (PSO + dispatch + UAV readback),
cube and 2D-array textures. Render graph: 25 passes, 19 resources, with
compile-time validation for pass cycles, missing producers, and copy-format
mismatches — all three failure modes exercised by gates. Passes: shadow map
(1024², single map), forward PBR (GGX, split-sum IBL with a BRDF LUT, 16-tap
Vogel PCF with interleaved gradient noise), source-cubemap sky, motion vectors,
Karis-average bloom (5 mips), ACES tonemap, and three exclusive AA modes (FXAA,
SMAA edge/weights/blend, TAA with YCoCg clipping). Instanced draws with batch
splitting on pipeline + buffers + textures. Frustum culling at extract
(`visible=33 skipped=31` of 64 in the live gate). RGBA16F scene colour, sRGB
handling verified against an HLSL implementation by GPU readback.

**Assets.** glTF (validated: accessor, view and index overruns all rejected)
and OBJ meshes, PNG via WIC with full mip chains, `SOLC` cooker and `SOLP` pak
format, virtual mounts with containment enforcement, handle-based mesh store
with generation counters and an unload path.

**Scene and gameplay.** 512-instance world with parent/child hierarchy
(cycle-rejecting), interned names, prefab extract/spawn with prefix remapping,
text scene files. CPU physics: AABB/sphere/capsule shapes, rigid bodies with
gravity and resting contacts, triggers with enter/stay/exit, raycasts against
all three shapes, BVH broadphase, layer/mask filtering. Character controller
with step and slope handling. Three cameras (follow, orbit, FPS).

**Platform and runtime.** Win32 window with borderless/fullscreen/vsync
toggles, XInput gamepad with deadzone handling, XAudio2 one-shots (16 voices,
32 sounds), cvars with file → CLI → default precedence, frame arena, fixed +
variable update split, PIX markers, async shader compile on a worker thread with
hot-reload and a disk cache, an 8×8 bitmap debug overlay.

### What is absent

No job system or worker-thread scheduler. Three files in the tree touch
threading primitives — `audio-xaudio2` (callbacks), `core/log.cpp` (a mutex),
`shader_hot_reload_dxc` (one compile worker) — and none of them is a scheduler.
The frame loop is single-threaded.

Also absent, entirely: skeletal animation and skinning; any animation system;
particles; UI; fonts and text layout; navmesh and pathfinding; networking;
scripting; shadow cascades; LOD; occlusion culling; SSAO/SSR/GI; reverse-Z;
multiple render targets; an editor.

**On text specifically**, because it decides one of the games below: the only
glyphs that exist in the engine are hand-typed 8×8 bitmaps in
`packages/debug-draw/src/stats_overlay.cpp:30-44`, covering the digits and
exactly the letters the debug overlay prints (F, P, S, C, U, M, E, G, R, X, N,
A). There is no font loader, no glyph atlas and no layout.

### What is half-built or out of place

**`content.pak` is shipped and read only by a gate.** `create_pak_loader`
appears in the live tree in exactly one place outside gate code, and that place
is inside `run_pak_gate` (`main.cpp:2171`) operating on a synthetic in-memory
pak. The running application uses
`engine::assets::filesystem::create_asset_loader` (`main.cpp:5557`).
`run_pack_gate` (`main.cpp:2217`) reads the real `content.pak` from the
executable directory purely to prove it exists and parses.

This is deliberate and recorded. `docs/ROADMAP.md:229` (Build #5) states
"Sandbox still mounts loose files for the live draw" and lists under **Do not
(still)**: "loading the forward pass from SOLC". So it is a capability gap
honestly registered, not a defect — but the consequence for a shipping game is
concrete: the install carries both forms.

**The cooker's input list is five hard-coded paths.**
`packages/cook/src/main.cpp:127-133` is an explicit `&&` chain over `cube.obj`,
`cartoon_husky.gltf`, `albedo.png`, `Cartoon_Husky_Albedo1.png` and a generated
beep. There is no manifest and no directory walk. It cooks `Albedo1.png` while
the runtime loads `Albedo1` through `Albedo4`.

**No compressed texture formats, which is the ceiling on shippable art.**
`rhi::Format` has five entries (`resources.hpp:19`): `Unknown`,
`RGBA8_UNORM`, `RGBA8_UNORM_SRGB`, `RGBA16_FLOAT`, `D32_FLOAT`. There is no BC1,
BC5 or BC7, and no `VertexFormat` beyond three float widths. Every texture is
uncompressed RGBA8.

The cost is measurable from the live gate: `Albedo PNG gate: 2048x2048
rgba=16777216` — 16.78 MB for the top mip of a single albedo, and `Mip gate:
2048x2048 mips=12` confirms a full chain, so ×4/3 ≈ **22.4 MB of VRAM per
2048² texture**. The sandbox loads four husky albedos: ≈ 89 MB for four
textures on one character. BC7 at the same dimensions is 4 bits per pixel
against 32, so under 6 MB with mips — a 3.75× reduction. Nothing in the tree
can express that format, so a real art budget cannot be met by tuning; it needs
a new `Format` entry, a decoder path in the cooker, and BC-aware mip handling.

**Shaders ship as source and are compiled on the player's machine.** Measured
from a real `cmake --install --prefix`:

| Component | Size | Share |
|---|---|---|
| `content.pak` (gate-only) | 17.17 MB | 47% |
| `dxcompiler.dll` + `dxil.dll` | 15.83 MB | 44% |
| loose `content/` (the live path) | 4.01 MB | 11% |
| `game.exe` | 0.74 MB | 2% |
| **Total** | **36.34 MB, 67 files** | |

18 `.hlsl` files ship in plaintext. The cooker handles meshes, images and
audio — **not shaders**. First launch compiles every shader into
`.cache/shaders` next to the executable.

**`game.exe` is a console application.** `dumpbin /headers` reports
`3 subsystem (Windows CUI)`. There is no `WIN32_EXECUTABLE` anywhere in the
build. The player build opens a console window, which — given S4 — is also the
only place a crash is ever reported.

### What games this can build

**A 2D platformer — buildable, awkwardly.** There is no 2D or sprite pipeline,
so it would be quads on an orthographic camera through the 3D forward path. The
16-material cap means 16 distinct textures unless you hand-atlas, and with no
compressed formats each 2048² atlas costs 22.4 MB of VRAM. The blocker is not
rendering: it is that a platformer needs a score, a menu and a pause screen, and
there is no text. Transparency is half-present: `BlendMode::Alpha` exists in the
RHI and is implemented in D3D12 (`device_d3d12.cpp:2277`), but its only consumer
in the whole tree is the debug stats overlay (`stats_overlay.cpp:129`) — the
forward pass has no transparency handling and no back-to-front sorting, and the
map lists it as an open Ready row (`ENGINE_MAP.md:144`). Sprite cutouts would
have to be alpha-tested in the shader.

**A third-person action game with 200 enemies on screen — not buildable, for
two independent reasons.** 200 enemies need 200 of the 256 physics bodies, which
must also hold the player, every projectile and every piece of level collision.
And there is no skeletal animation, so the enemies cannot be animated
characters. Either reason alone is disqualifying.

**A text-heavy RPG — not buildable.** No font rasterizer, no glyph atlas, no
text layout. The one reason.

**A single-room 3D physics puzzle or walking-sim vertical slice — buildable
today.** This is the shape the sandbox already is: a few dozen rigid bodies, a
character controller, three cameras, shadowed PBR with IBL, three AA modes,
audio one-shots, under 512 instances, under 256 bodies, under 16 materials, and
nothing that needs a glyph on screen.

### External comparison

**Job scheduling.** Godot ships `WorkerThreadPool`, which "allocates a set of
Threads on project startup" and supports group tasks "useful for iterating over
many elements". Unity ships the C# Job System with `IJobParallelFor`. Unreal
ships the TaskGraph. Sol has none. This is a deficiency, not a trade: every
peer in the stated bar has one, and the 200-enemy case is exactly the workload
that needs it even before the body cap bites.

**Shader shipping form.** Unity's documented behaviour is that "at player build
time, all 'not yet compiled' shader variants are compiled, so that they are in
the game data". The standard counter-argument — that PC hardware variety
precludes shipping precompiled shaders — is about driver-level ISA, not about
the intermediate: DXIL is precisely the shippable intermediate for D3D12, and
Unity and Unreal ship it. Sol ships the HLSL *text*, one full compilation stage
earlier than any reference engine, plus the 15.8 MB compiler to process it. That
is a deficiency.

**Where the comparison favours this tree.** The rendering feature set is deeper
than the stage would predict — split-sum IBL, motion vectors, TAA and SMAA, and
a render graph that rejects cycles and format mismatches are not typically
present in an engine that has not yet drawn a glyph. Per the standard, "excellent
for its size" does not raise the grade; it is stated here because it is true and
because it explains why the calibration counter-argument in section 7 is strong.

## 6. Portability — B (Solid)

### What was measured

**Platform-specific code is genuinely confined.** 16 includes of
`windows.h` / `d3d12` / `dxgi` / `dxcapi` / `wincodec` / `xaudio2` / `xinput` /
`wrl` across the whole tree, distributed as: `rhi-d3d12` 5, `shaders-dxc` 4,
`platform-win32` 3, `audio-xaudio2` 2, `assets-png-wic` 2. **Zero outside those
five backend packages.** Machine-checked across 140 source files by the
`graphics-api-isolation` invariant. There are no `_WIN32` conditionals outside
the backends either — the sandbox's two `#ifdef`s are `ENGINE_HAS_*` feature
macros, not platform tests.

**The abstraction is API-neutral in substance, not just in naming.**
`GraphicsPipelineDesc` carries counts (`constant_buffer_count`,
`shader_resource_count`, `structured_buffer_count`), not root signatures.
`Format`, `ResourceState` and `SamplerDesc` are vocabulary any of the three
modern APIs can satisfy. `resources.hpp:18` even carries a forward note for the
second backend's author about flip-model swapchains rejecting `_SRGB` formats.

**The portability debt is inventoried, in cost order, and correct.**
[`docs/ARCHITECTURE.md:130-160`](../ARCHITECTURE.md) ("Swap cost today") names
six obstacles. I verified the two most checkable against primary sources:

- **SPIR-V.** The doc says the work is "`-spirv` plus the `-fvk-*-shift`
  binding shifts, since D3D's separate `b`/`t`/`s` register spaces all collide
  at binding 0 in Vulkan. No shader edits." DXC's own documentation confirms the
  SPIR-V backend "is now supported and enabled in official release builds and
  can be used out-of-the box", invoked with `-spirv`. So the *already-shipped*
  `dxcompiler.dll` can produce SPIR-V; the claim is exactly right and the work
  estimate is accurate.
- **NDC Y.** The doc calls this "the one clip-space convention that is not
  already portable" and states that depth range, matrix order and texture origin
  agree across D3D12, Vulkan and Metal. Confirmed: Vulkan's clip-space Y points
  down, and not correcting for it means "your image will be flipped and your
  face culling order will be backwards". `Mat4::perspective` (`mat4.cpp:47`)
  produces a right-handed [0,1]-depth projection — the D3D and Metal
  convention — so Vulkan is the only one needing the flip. The doc is right, and
  right about it being the *only* one.

The remaining four items (descriptor sets, barrier stage scope, `present()`
returning `void` with no channel for `VK_ERROR_OUT_OF_DATE_KHR`, and resize
being window-event-driven "which is not sufficient on Wayland") are specific,
correctly reasoned, and correctly ordered by cost. Two D3D12-isms —
`IDevice::frame_slot()` and `ICommandList::set_sampler` — were removed
pre-emptively rather than left for that author.

### Findings

**P1 — High. `cmake -B build` fails at configure on Linux and macOS, before
anything compiles.**

`cmake/EngineRuntimeApp.cmake:30` links a namespaced target unconditionally:

```cmake
target_link_libraries(${TARGET} PRIVATE
    engine::engine
    engine::assets-filesystem
    ...
    engine::assets-png-wic      # line 30 — no guard
    ...
)
```

while the root `CMakeLists.txt` creates that target only on Windows:

```cmake
if(WIN32)
    add_subdirectory(packages/assets-png-wic)
endif()
```

The four sibling backends in the *same function* are guarded —
`if(TARGET engine::audio-xaudio2)`, `if(TARGET engine::physics-cpu)`,
`if(TARGET engine::platform-win32)`, `if(TARGET engine::rhi-d3d12)`. This one
was missed.

A namespaced target that was never created is a hard CMake generate-time error,
not a warning. Reproduced in a minimal project on this machine (section 9):

```
CMake Error at CMakeLists.txt:6 (target_link_libraries):
    engine::missing-pkg
  but the target was not found.  Possible reasons include:
```

I machine-checked the whole build graph for this class rather than trusting one
reading. Every `engine::X` reference in `cmake/*.cmake` and
`packages/*/CMakeLists.txt` was cross-checked against whether `packages/X` is
added unconditionally, with the referencing line's own `if()` context tracked.
The scan returned exactly two hits, and one dies on inspection:
`packages/cook/CMakeLists.txt:10` also references `engine::assets-png-wic`
unguarded, but `cook` itself is only added inside `if(WIN32)`, so that line is
unreachable on a non-Windows host. **One real offender: one line, one file.**

*Why this is High.* The stated goal is "mainstream Linux and macOS". This is
step one of that work, it fails before a compiler is invoked, and nothing in the
repository would catch it: `--gates` needs a GPU, the invariants do not model
conditional CMake targets, and the `configure-options` CI job — which exists
precisely to keep the modularity claim honest — runs only on `windows-latest`,
where `if(WIN32)` is always true. It is also absent from ARCHITECTURE.md's
obstacle list, which covers the second *GPU backend* and not the first
non-Windows *configure*.

**P2 — Medium. The sandbox includes two backends unguarded, so fixing P1 moves
the failure rather than removing it.**

`packages/sandbox/src/main.cpp` guards four backend includes behind
`ENGINE_HAS_*` (lines 60, 64, 68, 72) but includes two unguarded:

```cpp
#include <engine/assets/png/image_loader_png.hpp>        // line 30
#include <engine/shaders/dxc/shader_compiler_dxc.hpp>    // line 54
#include <engine/shaders/dxc/shader_hot_reload_dxc.hpp>  // line 55
```

So with `-DENGINE_RHI_D3D12=OFF`, or on any non-Windows host, the app does not
compile even if the CMake graph is made coherent. The CI job's own comment
states this ("with a backend switched off the sandbox does not compile (its DXC
and PNG includes are unguarded). That is a real gap"); I confirmed it in the
tree rather than taking the comment's word.

**P3 — Low. A D3D-convention projection lives in layer 0.**
`math::Mat4::perspective` is shared by every backend, so a Vulkan backend cannot
change the convention without affecting D3D12; the flip belongs in the backend's
viewport or in `common.hlsli`. Correctly identified in ARCHITECTURE.md as the
NDC-Y item, and the doc points at the right file for the fix.

### External comparison

**Godot 4's driver split** is the reference for "how far does clean isolation
get you". Godot reached a working D3D12 driver *after* refactoring
RenderingDevice, and has since added a native Metal backend. Where this tree
differs: Sol's isolation is measurably tighter at the source level (16 platform
includes, zero leaks, machine-checked), but Godot's is validated across three
drivers and three host platforms, and Godot's *build system* configures on all
of them. Sol's does not — which is the whole of P1, and it is why the tighter
source isolation does not yet translate into a higher grade than Godot's would
get.

### What is genuinely good here

The "Swap cost today" section is the best single document in this repository. It
does the thing portability sections almost never do: it names the obstacles that
remain, in the order they will cost, at the level of specific API semantics —
that `ResourceState::ShaderRead` does not say which stage reads, so a Vulkan
backend must over-synchronise; that `present()` returning `void` leaves no
channel for `VK_ERROR_OUT_OF_DATE_KHR`; that event-driven resize is not
sufficient on Wayland. Each of those is a thing a competent Vulkan author would
otherwise discover the hard way.

### What was measured

I ran the documented path rather than reading it. Every command copy-pasted
from README.md worked on the first attempt:

| Step | Result |
|---|---|
| `cmake --build build --config Debug` | clean, **0 warnings** |

The last row matters most and is the row most projects cannot produce: the

**The docs are accurate where they make checkable claims.** README says the
sandbox renders "63 huskies plus a checker floor" — the live gate reports

`ENGINE_*` option off, and running the invariants — which is exactly the three
jobs in `ci.yml`. The `cmake --install` / `.\dist\game.exe` instruction is
backed by real `install(TARGETS game RUNTIME DESTINATION .)` rules.

**CI is honest about its own limits, in writing, at the point of the gap.**
`ci.yml` explains why `--gates` is not run and why adding it would not work (the
D3D12 backend skips `DXGI_ADAPTER_FLAG_SOFTWARE` adapters and hosted runners
have no hardware one), and what the fallback is if the runner image loses DXC.
The `configure-options` job's comment states plainly what it does *not* cover.

**Repository hygiene.** `.gitignore` covers builds, IDE state, secrets, binaries
and the gitignored research library, and each unusual entry carries the reason
(`config.cfg` unanchored on purpose, because the engine looks in two places).
`.gitattributes` normalises to LF, forces CRLF for Windows shells with the
reason (`cmd.exe` mis-parses multi-line blocks in an LF-only `.bat`), and marks
binaries explicitly rather than relying on git's NUL heuristic. Third-party code
is one vendored file, licensed and disclosed in README.

### Findings

**D1 — Medium. `.clang-format` describes a style the tree does not use, and no
document mentions it.**

Measured with clang-format 22.1.1 over 120 non-vendored files:

| Configuration | Nonconforming files | Violation sites |
|---|---|---|
| `.clang-format` as committed | **103 of 120** | **5,686** |
| plus `PointerAlignment: Left`, `ReferenceAlignment: Left` | 90 of 120 | 2,778 |

The figure is not an artefact of one clang-format build: **clang-format 20.1.8
(the Visual Studio 18 bundled binary) and 22.1.1 (standalone LLVM) both report
103 of 120**, so a contributor gets the same result from either tool on this
machine.

So **51% of all violations** come from one setting. `BasedOnStyle: LLVM` implies
`PointerAlignment: Right` (`Type *name`); the tree writes `Type* name`, and the
census is not close:

| Style | Occurrences |
|---|---|
| `Type* name` | 530 |
| `Type *name` | 33 |
| `Type& name` | 797 |
| `Type &name` | 6 |

The two minority counts are dominated by multiplication and bitwise-AND
expressions that match the pattern, so the tree's convention is effectively
unanimous, and the config states the opposite.

The remaining 2,778 sites are three further identifiable settings —
short case labels on one line (`case LogLevel::Info:  return "INFO";`),
continuation indent rather than open-bracket alignment, and assignment-break
preference. Sampled diffs are in section 9; some files
(`packages/scene/src/world.cpp`) already conform exactly with the two-setting
delta.

And `.clang-format` is referenced in **no** documentation: not README.md, not
CLAUDE.md, not `.claude/rules/`, not anywhere under `docs/`. Nothing tells a
contributor whether to run it. Running it would rewrite 86% of the tree.

**D2 — Low. Half the shipping payload is not read by the running game.** The
36.34 MB install is 47% `content.pak` (gate-only, per section 5) and 44% shader
compiler, against 11% of loose content that the game actually loads. Deliberate
and recorded in the decision log, so this is a payload observation rather than a
defect — but it is what a player would download.

**D3 — Low. The player binary is a console application.** `dumpbin /headers`
on `build/bin/Release/game.exe`: `3 subsystem (Windows CUI)`. A console window
accompanies the game. Given S4 (stderr is the only log sink) that window is also
the only crash report anyone gets, so the two findings pull in opposite
directions and should be resolved together.

**D4 — Low. A documented command leaves 36 MB of untracked, addable files.**
README documents `cmake --install build --config Release --prefix dist`.
`.gitignore` ignores `*.exe`, `*.dll` and `*.pak`, but not `dist/` and not the
PNG, glTF, WAV, OBJ or HLSL files the install copies. CLAUDE.md's standing rule
against reflexive `git add -A` is the only thing standing between that and a
duplicated content tree in history.

### External comparison

**CI scope.** Godot's CI builds and runs checks across Linux, Windows, macOS,
Android, iOS and Web, and executes unit tests. Sol's CI is one OS, no test
execution, and it says so. Where this differs: the deficiency is real (single
platform, no test run), but the *reason* is a genuine environmental constraint
that Godot does not share — Godot's tests do not need a hardware D3D12 adapter.
The mitigation Sol chose in response is the more interesting part: rather than
accept a CI that proves nothing, it moved eleven architectural properties into a
compiler-free source analysis that a hosted runner *can* run. That is a
reasonable answer to a constraint, not a gap left open.

### What is genuinely good here

`tools/check-invariants.ps1` again, from the developer's side rather than the
architect's. Four of its eleven checks are things I have not seen in a
comparable repository: it resolves every markdown link across the tree (skipping
fenced code, because a C++ lambda `[](const Foo& bar)` is shaped exactly like a
link — a detail someone learned the hard way); it recounts the LOC figures the
ROADMAP claims and fails if they drift ("These figures went stale twice
before"); it validates that every design spec carries a resolved `Status:`
("Four specs sat at 'not yet implemented' long after shipping"); and it checks
that grades agree between generated report files, because "a grade that
disagrees between the hub and the page it links to is the one failure a reader
cannot detect for themselves". Each check exists because a specific thing went
wrong once and was made impossible afterwards.

**T1 — Medium. The one root-level config that would rewrite the tree is invisible

### External comparison

There is no engine to compare against here — no reference implementation in the
peer group ships an AI instruction set. The nearest available reference is the
documented Claude Code convention set itself: `CLAUDE.md`, path-scoped rules

I record that as a weaker comparison than the code dimensions received:

was compared. It caps at A− and does not bind at B+.

Two things, and the second is unusual.

First: rules that state absolute numbers *and* are held to them by the
compiler. `renderer-boundaries.md` says `InstanceData` is 144 bytes; the header

Second: the tooling has visibly corrected itself, with the reasoning preserved

the ceiling, as originally written with no severity floor, "fired on **all six

accept the flat result." That is an instruction set that has learned something
about itself and written the lesson where the next reader will hit it. On this
run G3 fired on exactly one dimension, which is the intended behaviour.

## 9. Cross-cutting

**`.clang-format` produces two findings in two dimensions from one fact.** D1
(the config disagrees with 86% of its own tree and no document mentions it) and
T1 (the rules a session loads before editing C++ do not mention formatting) are
the same root cause seen from the human and the agent side. Both dimensions
landed at B+ and both name this as the single criterion that kept them out of
the band above. One fix moves two grades.

**S4 and D3 pull against each other.** `game.exe` being a console application
(D3) is a wart for a player build; but stderr is the only log sink (S4), so the
console window is currently the only crash report that exists. Making the player
a GUI subsystem app *before* adding a file logger would convert every crash from
visible-but-transient to entirely silent. Order matters: file logger first.

**Silent-by-design failure appears three times.** A null pipeline disables a
pass (S2); the cooked pak is shipped but not read (section 5); the shader disk
cache falls back to recompiling with a warning. All three are deliberate, and
two of the three are documented. The pattern is coherent — this engine prefers
degrading to dying — but S2 is the one where the degradation has no log line at
all.

**Single-threadedness is load-bearing in two directions.** It removes an entire
class of stability failure, which flatters S; and it is a named capability gap
against all three reference engines, which is part of why C is where it is. It
should not be credited twice, and section 3 does not credit it at all.

## 11. Calibration notes

**Distribution.** A−, B+, B+, B+, B, C+ — **five of six at B or above**. That
is over half, which the standard names as the documented symptom of leniency
bias rather than as evidence of a good tree, so it was re-examined rather than
noted.

The re-examination: three of the four B+ grades are "top of Solid, missed
Exemplary on one named criterion", and in each case the criterion is named
concretely rather than gestured at. Two of the three (D and T) miss on the *same
underlying fact*, which is coherent rather than lenient — but it does mean the
distribution is less independent than six grades suggest. If `.clang-format`
were addressed and documented, D and T would both be candidates for the band
above, and the distribution would look worse, not better. That is a real
weakness of this grade set and it is stated here rather than resolved by
lowering something arbitrarily.

**Clustering.** Four of six sit in the Solid band (B+, B+, B+, B) — exactly the
central-tendency threshold. Both outliers were re-derived from evidence rather
than argued away: C+ from an inventory of absent subsystems against a named peer
group plus two named games with one disqualifying reason each; A− from a
machine-checked 49-edge graph plus a cited case of a reference engine
retrofitting the same design. Both held.

Why the cluster is real: S, P, D and T are four views of one tree, and that tree
has one consistent character — careful, heavily commented, thoroughly gated,
single-platform, single-backend, small. Four dimensions landing in the same band
is what that character should produce. What would be suspicious is four grades in
one band supported by evidence of differing quality; that is not the case here.

**The best argument against my highest grade (A−, Architecture) is that the
seam has never been exercised.** Every claim supporting it is about a
counterfactual: that a second backend would be a new package rather than a
rewrite, that `renderer` will never need a graphics header, that a system can be
removed without dragging another out. Godot earned its architecture standing by
shipping three drivers through the same interface and publishing what the split
cost; Sol has one driver and a document predicting the cost. And there is direct
evidence that the modularity has only been tested in the direction it already
works: P1 means the build system cannot *configure* off Windows because of one
unguarded line — which is what an untested seam looks like from the outside. A−
for a strong hypothesis is generous, and I am recording that rather than
defending it.

**The best argument against my lowest grade (C+, Capabilities) is that
everything present works and is provably correct.** 70 gates asserting real
values, passing in three configurations including a fresh install; a completely
silent D3D12 debug layer; and a renderer with split-sum IBL, Vogel PCF, motion
vectors, TAA, SMAA and a validating render graph — depth that most engines do
not have at any stage, let alone before drawing their first glyph. Grading
Capabilities on absences means a tree that does a narrow thing excellently
scores below one that does many things badly. If the question were "how much of
what is here can I trust", C+ understates it substantially. It is the right grade
only because the question the dimension asks is "what games can be built", and
the honest answer is one shape.

**The 29 Aug run's other two actions: one done, one not.** Its second action was
to correct the "four files" figure for adding a render pass; `renderer-boundaries.md`

forward.

extracted all 49 dependency edges, performed the deletability test on two
packages rather than reading the layering, and found a citable case of a
reference engine (Godot 4) retrofitting the same renderer/driver split and
publishing what the retrofit cost. The code changed little; the basis for the
grade changed a lot.

**Developer setup and AI tooling, C+ → B+, are partly earned and partly better
measurement.** Earned: the wrong claims the 29 Aug run found in the instructions
have been corrected, which was the substance of its AI-tooling grade. Better
measurement: this run executed the whole documented path including
`cmake --install` and ran the gates from the installed layout, which the previous
run does not appear to have done.

**Portability, B− → B, on a corrected reading and one new finding.** The 29 Aug
run said the hardware layer "quietly encodes Windows-only concepts"; this run
finds the opposite at the source level — 16 platform includes, zero outside five
backend packages — and finds the remaining API-shape debt precisely inventoried

blocked A− regardless of evidence.
