## 3. Per dimension

### S — Stability — Fragile — D+

#### S1 — No sRGB / gamma handling anywhere in the render path — **Critical**

The engine runs a physically-based lighting model in the wrong colour space, at
both ends of the pipeline, and nothing detects it.

Evidence, all from the tree:

- [`packages/rhi/include/engine/rhi/resources.hpp:11`](../../packages/rhi/include/engine/rhi/resources.hpp) —
  `enum class Format : u8 { Unknown, RGBA8_UNORM, RGBA16_FLOAT, D32_FLOAT };`
  There is no sRGB variant in the RHI at all, so no target can be created as one.
- [`packages/rhi-d3d12/src/device_d3d12.cpp:998`](../../packages/rhi-d3d12/src/device_d3d12.cpp) —
  `sd.Format = DXGI_FORMAT_R8G8B8A8_UNORM;` The swapchain is non-sRGB.
- [`packages/rhi-d3d12/src/device_d3d12.cpp:249`](../../packages/rhi-d3d12/src/device_d3d12.cpp) —
  `case Format::RGBA8_UNORM: return DXGI_FORMAT_R8G8B8A8_UNORM;` — the only
  8-bit mapping, non-sRGB.
- [`packages/renderer/src/standard_frame.cpp:33-38`](../../packages/renderer/src/standard_frame.cpp) —
  `ldr_color` is created as `rhi::Format::RGBA8_UNORM`.
- `grep -rn "srgb\|SRGB\|1.0/2.2\|gamma"` across all 17 `.hlsl` files returns
  **no** transfer-function application. The only `pow` calls are Fresnel
  (`forward.hlsl:116`) and the sun disk (`sky.hlsl:39-40`); the only
  luminance work is Rec.709 dot products.
- Albedo is sampled directly into linear PBR maths:
  [`packages/sandbox/content/shaders/forward.hlsl:15`](../../packages/sandbox/content/shaders/forward.hlsl)
  declares `Texture2D albedo_map : register(t0)`, and `forward.hlsl:132-139`
  feeds that sample straight into `f0 = lerp(0.04, albedo, metallic)` and
  `diffuse_color = albedo * (1.0 - metallic)`.
- `grep -rin "srgb\|gamma\|colour space\|color space" docs/ *.md .claude/`
  returns **nothing**. This is not a recorded decision anywhere, including the
  ROADMAP decision log which does record *why* for shipped work.

The tone-mapping curve at
[`packages/sandbox/content/shaders/tonemap.hlsl:21-28`](../../packages/sandbox/content/shaders/tonemap.hlsl)
is Krzysztof Narkowicz's ACES fit, byte-for-byte (`a=2.51, b=0.03, c=2.43,
d=0.59, e=0.14`). Its author states directly: **"you need to multiply by
exposure before the tone mapping and do the gamma correction after,"** and that
the curve was fitted after *removing* the 2.4 gamma from the Rec.709 D65
ODT output. The fit is linear-in, linear-out. This engine does neither the
exposure multiply nor the gamma correction.

So there are two independent errors:

1. **Input**: sRGB-authored PNG albedo is sampled as if linear. sRGB midtones
   are numerically far above their linear equivalents (sRGB 0.5 ≈ linear
   0.214), so every diffuse and Fresnel term is computed on inflated albedo.
2. **Output**: the linear tonemapped result is written to a UNORM target and
   presented with no OETF, so the displayed image is darker than intended.

They partially cancel, which is exactly why this ships unnoticed. But the
consequence is that the split-sum IBL, GGX specular, Smith visibility, energy
conservation and `alpha = r²` remapping — all of which have gates
(`PBR gate: ggx_peak=yes metal_f0=yes points_spec=yes energy=kd_1-F alpha=r^2
(pass)`) — are proven correct as *formulas* while being fed and consumed in the
wrong space. The gates assert the maths and cannot see the colour space. Of 67
gates, none references colour space.

Rated Critical because it is present and wrong in the subsystem the project
leads with, it is silent, it is ungated, and it is nowhere recorded as
deliberate. **G5 therefore caps this dimension at D+.**

#### S2 — `bind_aa_constants` does not stop its callers; its own comment says it does — **Medium (latent)**

[`packages/renderer/src/render_graph.cpp:326-334`](../../packages/renderer/src/render_graph.cpp):

```cpp
void bind_aa_constants(PassContext& ctx, const rhi::ITexture& src) {
    const aa::Constants constants = aa::make_constants(src.width(), src.height());
    const rhi::FrameAllocation slice = ctx.device.alloc_frame_memory(sizeof(constants));
    if (!slice.buffer) {
        return;  // constant ring exhausted this frame; skip the pass
    }
    ...
}
```

It returns `void`. All four callers ignore it and draw regardless —
`record_fxaa` (`:350`), `record_smaa_edge` (`:360`), `record_smaa_weights`
(`:370`), `record_smaa_blend` (`:381`), each of which is
`set_pipeline` → `bind_aa_constants` → `set_shader_resource` →
`draw(3)`. On ring exhaustion the pass draws with root constant-buffer slot 0
never set. The comment claims it skips the pass; it cannot.

This is the only one of thirteen recorders that gets this wrong. Every sibling
handles the identical case correctly by returning from the recorder itself —
`record_sky:277`, `record_bloom_downsample:293`, `record_bloom_upsample:311`,
`record_taa:399`, and the shared `record_draws:164`.

**Reachability, measured.** The ring is 1 MiB per in-flight slot
([`device_d3d12.cpp:42`](../../packages/rhi-d3d12/src/device_d3d12.cpp),
`kFrameRingBytes = 1024 * 1024`) with 256-byte alignment (`kBufferAlign`,
`:20`). Worst case at the current cap — 512 instances, every one a distinct
material/mesh key, so batch count equals instance count:

| Consumer | Bytes |
|---|---|
| instance array, 512 × 144 | 73,728 |
| shadow, 512 × align256(80) | 131,072 |
| forward, 512 × align256(336) | 262,144 |
| motion, 512 × align256(160) | 131,072 |
| sky + bloom (5 down, 4 up) + TAA + AA | ≈ 3,800 |
| **total** | **≈ 601,800 of 1,048,576 (57 %)** |

This matches the engine's own arithmetic at `device_d3d12.cpp:30-42` (1,024
bytes per batch across the three geometry passes). **So the ring cannot be
exhausted today and the defect is latent, not live.** Two facts make it worth
reporting anyway: the crossover is ≈1,024 batches, and `kMaxInstances` moved
64 → 512 one commit ago (`5febb3e`) — the next raise makes it live; and the AA
passes allocate *last* in the frame, so they are the first to starve when the
ring does run dry. The code path with the bug is the path most likely to hit it.

Exhaustion itself is handled well: `alloc_frame_memory:1713-1721` latches
`frame_ring_exhausted_` and logs the used bytes, the capacity, and an instance
estimate, once per frame.

#### S3 — Trigger events are dropped silently, while sibling overflows in the same file warn — **Medium**

[`packages/physics-cpu/src/physics_cpu.cpp:1045-1050`](../../packages/physics-cpu/src/physics_cpu.cpp):


`kMaxTriggerEvents = 256`
([`packages/physics/include/engine/physics/physics.hpp:19`](../../packages/physics/include/engine/physics/physics.hpp)).
Past that, enter/stay/exit events vanish with no log. The same file reports its
other capacity limits: the contact buffer calls
`warn_physics_capacity("contact buffer")` (`:978`) and BVH traversal calls

Consequence for a game: past 256 trigger transitions in a frame, a door does
not open and there is nothing in the log to explain it. That is the failure
class the audit weights above crashes — a crash is reported, this is not.

```cpp

    static bool warned = false;
```

#### S5 — `intern_name` aborts on overflow; every sibling capacity in `scene` returns `false` — **Low-Medium**

[`packages/scene/src/world.cpp:106`](../../packages/scene/src/world.cpp):
`ENGINE_ASSERT_MSG(world.names.count < NameTable::kCapacity, "scene name intern overflow");`

`ENGINE_ASSERT` is **live in Release**. There is no `NDEBUG` guard anywhere in
[`packages/core/include/engine/core/assert.hpp`](../../packages/core/include/engine/core/assert.hpp),
and `assert_fail` calls `std::abort()`
([`packages/core/src/assert.cpp:16`](../../packages/core/src/assert.cpp)). 77
call sites across the tree are therefore live in the shipping player. This is
deliberate and stated in-code (`cvar.hpp:53`: "ENGINE_ASSERT is always active
and assert_fail is `[[noreturn]]`").

**What Pass 4 killed:** the obvious version of this finding — "a scene file can
abort the player" — is **false**. `read_world` bound-checks before every add:
`if (out.instance_count >= kMaxInstances) return false;` and
`if (out.material_count >= kMaxMaterials) return false;`
([`packages/scene/src/scene_file.cpp:243`, `:257`](../../packages/scene/src/scene_file.cpp)),
and `instantiate_prefab` checks
`dest.instance_count + named > kMaxInstances` up front
([`packages/scene/src/prefab.cpp:126`](../../packages/scene/src/prefab.cpp)).
The name table is sized `kMaxInstances + 1` with `count` starting at 1
([`world.hpp:52-56`](../../packages/scene/include/engine/scene/world.hpp)), so
one unique name per instance fits exactly and neither loader path can overflow
it. That sizing is deliberate and correct.

What survives is narrower: `set_instance_name` interns a fresh string every
time and the table never reclaims, so game code that renames instances with
generated names — a respawn counter, a scoreboard label — aborts the process
after 512 distinct names. It is the only capacity in `scene` with no `bool`
escape; `add_instance`, `add_material`, `set_instance_parent` and both loaders
all degrade. Fixing it means changing a return type, which is a behaviour
change, so it belongs on the decision list rather than the plan.

#### S6 — Profiler scope stack unbalances past 8 nested scopes — **Low (unreachable today)**

[`packages/core/src/profile.cpp:24`](../../packages/core/src/profile.cpp)
drops the push silently when `depth_ >= kMaxScopes` (`kMaxScopes = 8`, `:11`),
but `end_scope` (`:33`) decrements whenever `depth_ != 0`. Push and pop
therefore desynchronise, and `accumulate` consumes `start_[depth_]` belonging
to a scope that is still open — timings are attributed to the wrong scope and
the F3 overlay shows wrong numbers with no indication.

Not reachable today: the deepest actual nesting is 3
(`engine.cpp:288` frame → `:406` render → `:419` extract). Reported because it
is silent and the failure is in the tool a developer would use to diagnose
something else.

#### What is genuinely good in S

This dimension is not weak because the author was careless — it is weak because
of one specific unnoticed thing. The stability work that *is* here is better
than most projects at this size:

- **Every capacity that was converted degrades, and a gate proves the
  degradation.** `main.cpp:616-618` records the reasoning: "Capacity limits
  used to abort the process, which also made them untestable: no gate can
  exercise a path that calls `std::abort()`. They now degrade, so these gates
  can prove the degradation is what it claims to be." The arena gate then
  asserts four separate properties including that a rejected allocation does
  not consume the bump pointer and that `sizeof(T) * count` overflow is
  rejected.
- **Device loss is handled correctly**, which most hobby engines never do.
  `device_lost()` is documented as latched and never clearing
  ([`rhi/device.hpp:68-72`](../../packages/rhi/include/engine/rhi/device.hpp)),
  and `engine.cpp:307-316` stops the loop with a Fatal log that explicitly
  tells the reader it is a driver reset and not a content error.
- **Numerical guards with recorded reasoning and a gate.**
  `Mat4::perspective` clamps three unguarded denominators
  ([`math/src/mat4.cpp:47-66`](../../packages/math/src/mat4.cpp)) rather than
  letting inf/NaN reach a constant buffer, and the Math guard gate asserts
  `normal_proj=1.830` against an independently derived value.
- **Content is treated as hostile.** glTF is validated before unpacking, with a
  gate covering accessor, view and index overruns separately. Mount paths block
  `..`, absolute components, UNC and rooted paths, each with its own gate
  assertion.
- **The frame ring and the extract arena both log why they dropped work**, and
  `extract.cpp:113-117` and `:262-264` explain that emitting nothing costs one
  frame while continuing would write through null.

#### External comparison for S

Godot, bgfx and Unreal all handle the sRGB question at the API layer: bgfx
carries `BGFX_TEXTURE_SRGB` and sRGB framebuffer support, and Unity/Unreal both
default to a linear workflow with automatic sRGB sampling and an sRGB
backbuffer. The difference here is not a deliberate trade — it is an absence,
and it is the one place where this engine's output is wrong rather than merely
smaller in scope. Against the stated Unity/Godot/Unreal bar this is a
deficiency, not a simplification.

On assert-in-release, the trade is genuinely defensible and matches shipped
practice at the strict end: Unreal's `check()` is active in Development and
`checkSlow()` is not, and several studio engines keep a subset live in shipping
precisely so corruption fails loudly. The 77 live sites here are almost all
programmer-error preconditions in the RHI (null resource, mismatched copy
extents, root-parameter overflow), which is the right category for it. The
concern is the one case (**S5**) where a *capacity* rather than a *precondition*
aborts.

#### A1 — Adding one render pass touches eight files across two packages — **Medium**

Measured, not estimated. `taa_pipeline` — the pipeline pointer for one real
pass — appears in seven files:

```
packages/renderer/include/engine/renderer/extract.hpp
packages/renderer/include/engine/renderer/render_snapshot.hpp
packages/renderer/src/extract.cpp
packages/renderer/src/render_graph.cpp
packages/renderer/src/standard_frame.cpp
packages/sandbox/src/main.cpp
packages/sandbox/src/world_extract.cpp
```

Plus `packages/sandbox/content/shaders/taa.hlsl` — **eight**.

The mechanism is a god-struct that grows per pass. `RenderSnapshot`
([`render_snapshot.hpp:128-147`](../../packages/renderer/include/engine/renderer/render_snapshot.hpp))
carries **13 named pipeline pointers** and 5 texture pointers, and
`extract_visible` ([`extract.cpp:46-70`](../../packages/renderer/src/extract.cpp))

describes the cost precisely — "add the `I<Thing>Pipeline*` field to **all
four** structs it passes through, and to the three hand-written copy blocks
between them" — and warns that missing a step "fails **silently**: every
`should_execute` predicate treats a null pipeline as 'feature disabled'".

Nothing checks it. The invariant script verifies include direction and CMake
edges; it cannot see that a field was added to three of four structs. That is a
foreseeable, nameable failure with no gate, test or check covering it — **G3
fires and caps this dimension at B+**.

#### A2 — Compute is implemented in the RHI and unreachable from the graph — **Medium**

`PassKind` is `enum class PassKind : u8 { Graphics, Copy };`
([`render_graph.hpp:29`](../../packages/renderer/include/engine/renderer/render_graph.hpp)).
There is no compute pass kind. `grep -rn "IComputePipeline\|dispatch\|Compute"
packages/renderer/` returns **nothing** — the renderer package does not
reference compute at all.

Meanwhile the RHI has `IComputePipeline`, `ComputePipelineDesc`,
`create_compute_pipeline`, `set_unordered_access` and `dispatch`, all
implemented in the 2,588-line D3D12 device. The **only** consumer in the tree is
[`packages/sandbox/src/main.cpp:1355`](../../packages/sandbox/src/main.cpp) and
`:1376` — `run_rhi_impl_gate`, which creates a compute pipeline and dispatches
`(1,1,1)` to prove the RHI can. Compute exists to satisfy its own gate.

This is over-engineering in the specific sense the audit asks about: an
abstraction with one implementation and no reachable consumer is a cost with no
buyer. It also blocks a class of technique (GPU culling, compute bloom, SSAO,
particle simulation, skinning) at the architecture level rather than the
feature level.

#### A3 — `packages/sandbox/src/main.cpp` is 5,361 lines — 28 % of the tree in one file — **Medium**

`wc -l` gives 5,361 lines / 232 KB, the second-largest file in the repository
after vendored `cgltf.h`. It holds all 67 gates, every pipeline description,
every shader path constant, and the demo. For comparison, the entire `renderer`
package is 2,551 lines across 16 files and the D3D12 backend is 2,642 across 5.

This is a maintainability liability rather than a correctness one, and it is
the reason `main.cpp` also dominates the formatter finding (**D1**): 2,522 of
its lines disagree with `.clang-format`.

#### What is genuinely good in A

- **The instancing design is portable by deliberate choice, and the reasoning
  checks out against primary sources.**
  [`render_snapshot.hpp:23-31`](../../packages/renderer/include/engine/renderer/render_snapshot.hpp)
  explains why the batch's first-instance index travels in the constant buffer:
  "D3D excludes StartInstanceLocation from SV_InstanceID, Vulkan includes it in
  gl_InstanceIndex, and Metal splits it out again. A base in the constant
  buffer reads the same on all three." I verified this independently: D3D's
  `SV_InstanceID` counts from 0 regardless of `StartInstanceLocation`, while
  Vulkan's `gl_InstanceIndex` starts at `firstInstance` — the DXC issue tracker
  carries the same conclusion and proposes emitting
  `gl_InstanceIndex - gl_BaseInstance` to reconcile them. The engine chose the
  option that needs no reconciliation. Very few projects at this scale get that
  right *before* the second backend exists.
- **The batching rationale rules out two plausible-but-wrong designs with
  measured reasons.** `extract.cpp:171-183`: adjacency batching produced "33
  batches for 33 draws — no batching at all" because the sandbox alternates
  albedo between neighbours; and sorting was rejected because "the key is made
  of pointers, and *ordering* pointers makes batch composition depend on
  allocator addresses, so it would vary run to run and any gate asserting batch
  counts would be flaky." That is a real engineering argument about test
  determinism, not a preference.
- **`should_execute` is a clean declarative way to make optional passes
  optional**, and every one of the 13 recorders null-checks its pipeline and
  its shader reads before touching them.
- **The static_asserts pin the C++/HLSL boundary**: `sizeof(InstanceData) ==
  144`, `sizeof(FrameConstants) == 336`, `sizeof(ShadowConstants) == 80`, and
  `world_extract.cpp:21` and `:29` assert that `scene` and `renderer` agree on
  point-light and history-slot counts. Struct-layout drift between C++ and
  shader code is a classic silent corruption; here it is a compile error.

#### External comparison for A

Against **bgfx** and **sokol_gfx**: both avoid the growing-snapshot problem by
passing resources as opaque handles bound per draw or per pass, so adding a
technique does not widen a shared struct. Sol's 13-pointer `RenderSnapshot` is
the cost of being strongly typed instead — every pipeline has a name, which
makes null-checking exhaustive and readable, and makes a missing one a
compile-visible field rather than a runtime handle lookup. That is a genuine
trade rather than a mistake, but the eight-file cost is the price and it grows
linearly.

Against modern render-graph practice (Our Machinery's write-up; Unity SRP's
`RenderGraph`; the frame-graph designs common since FrameGraph/Halcyon): passes
declaring compute work, including async-compute queue placement, is table
stakes, and GPU-driven culling through a compute pass is where the field has
gone. Sol's graph is a competent barrier-and-dependency scheduler
(missing-producer, copy-format-mismatch and cycle detection each have a gate)
but it schedules only Graphics and Copy. That is a deficiency against the bar,
not a trade.

### C — Capabilities — Working — C+

#### What actually exists, read from the code

**Rendering** — D3D12 forward renderer; render graph compiling 25 passes over

#### C1 — No block-compressed texture format exists — **High**

The RHI has four formats
([`resources.hpp:11`](../../packages/rhi/include/engine/rhi/resources.hpp)):
`Unknown, RGBA8_UNORM, RGBA16_FLOAT, D32_FLOAT`. There is no BC1–BC7, no ETC,
no ASTC, and no sRGB variant.

The cost is measurable from the engine's own gate output:

```
[INFO][assets] Albedo PNG gate: 2048x2048 rgba=16777216 (pass)
[INFO][render] Mip gate: 2048x2048 mips=12 expected=12 (pass)
```

16,777,216 bytes — **16 MB for one 2K albedo**, ~21 MB with the full 12-mip
chain, uncompressed. The sandbox uses four such albedos (~85 MB). BC7 at the
same resolution and quality would be ~5.6 MB mipped, roughly a 4× saving; BC1
~2.8 MB. A scene with twenty distinct 2K materials costs ~420 MB of VRAM here
against ~112 MB with BC7.

This is the single gap that most directly bounds what content can ship, and it
is why the dimension cannot reach Solid: it is a layer a professional would
rewrite before shipping, not extend.

#### C2 — Compute is unreachable from the graph — **Medium**

See **A2**. Listed here too because the capability consequence is distinct from
the architectural one: no compute-based technique can be expressed as an engine
pass, regardless of the RHI being ready for it.

#### C3 — Half-built and out-of-place inventory

- **MSAA is not expressible.** `TextureDesc`
  ([`resources.hpp:139-148`](../../packages/rhi/include/engine/rhi/resources.hpp))
  has no sample count. This is why AA is FXAA/SMAA/TAA only — a post-process
  set, not a choice.
- **`BlendMode` is `{Opaque, Alpha}`** only — no additive, no premultiplied.
  ENGINE_MAP lists "Transparency / alpha (forward; keep out of deferred)" as
  **Ready** at `docs/ENGINE_MAP.md:144`, i.e. not done.
- **Lighting is capped very low**: `kMaxPointLights = 4`
  ([`render_snapshot.hpp:21`](../../packages/renderer/include/engine/renderer/render_snapshot.hpp)
  and `scene/world.hpp:14`, asserted equal by `world_extract.cpp:21`), one
  shadow-casting directional light, no cascades, no spot lights.
- **Engine shaders live under the sandbox's content root** —
  `packages/sandbox/content/shaders/` holds `forward.hlsl`, `shadow.hlsl`,
  `motion.hlsl`, `taa.hlsl` and the rest. This is out of place by the project's
  own account: the rules file calls it "a known wart — do not 'fix' it in
  passing."
- **SPIR-V is declared and rejected**: the `shaders` interface carries a
  SPIR-V target and the DXC backend refuses it, logged during gates as
  `Shader target SPIR-V is not implemented (DXC backend emits DXIL only)`.

Open **Ready** rows that a project at this stage would normally have: file
logger (Foundation #6), transparency (Renderer #16), glTF skins/morphs
(Assets #10), world streaming (Scene #7), input actions (Input #2), 3D
positional audio (Audio #3), screen-space quads + font atlas (UI #2), terrain
(#3), CPU particles (#1), navmesh (#1), installer (#8), quality presets (#10).

#### C4 — What games can be built on this today

This is the section that matters most, so each verdict names its blocker.

**A physics-driven 3D puzzle game — a Portal-style test chamber, or a
Marble-Madness descendant.** **Buildable today.** Everything it needs is
present and gated: capsule and box bodies with gravity and restitution
(`Physics body gate: gravity=yes rest=yes floor=yes sphere=yes box=yes`),
triggers with enter/stay/exit (`Physics trigger gate: enter=yes stay=yes
exit=yes mask=yes solid=yes`), raycasts, a character controller with step and
slope (`Character gate: walk=yes jump=yes step=yes slope=yes grounded=yes`),
three cameras, glTF meshes, scene files with hierarchy and prefabs for
authoring chambers, and one-shot audio. The 512-instance cap and 4-point-light
limit are comfortable for room-scale scenes. The genuine constraint is that the
game cannot display a single character of text — no score, no hint, no menu —
so it ships as a pure-diegetic experience or not at all.

**A third-person action game with 200 enemies on screen.** **Not buildable**,
for one reason that is not the one you would guess. Instance capacity is fine —
512 instances, and the batching path measured `drawn=512 batches=…` in the
capacity gate. Physics is the wall: `kMaxBodies = 256`
([`physics/physics.hpp:18`](../../packages/physics/include/engine/physics/physics.hpp))
is a hard array bound, and `create_body` returns an invalid handle past it. 200
enemies plus the player plus projectiles plus level collision exceeds 256
quickly, and the trigger-event buffer (`kMaxTriggerEvents = 256`, dropped
*silently* — **S3**) saturates at exactly the density this genre generates.
Second blocker: no animation or skinning (Assets #10, Ready), so the 200
enemies cannot move as characters. Raising `kMaxBodies` is a constant; skinning
is a feature.

**A text-heavy RPG or any game with a UI.** **Not buildable.** There is no text
rendering of any kind — UI #2 "Screen-space quads + font atlas" is **Ready**,
meaning not started. The stats overlay draws with its own shader in
`debug-draw` and is not a general text facility. This blocks dialogue,
inventory, menus, tooltips, damage numbers and subtitles — and it is the one
missing piece that most broadly gates *genres* rather than *scenes*.

**A 2D platformer.** **Buildable with a named missing piece: alpha blending.**
The orthographic projection exists (`Mat4::ortho`, used for the shadow pass),
quads are trivially meshes, and the physics AABB path plus the character
controller's step/slope logic covers movement. But sprites need
`BlendMode::Alpha` against a sorted draw order, and `DrawBatch` has no sort key
or blend state — batch membership is pipeline identity, and there is no
back-to-front ordering pass. Transparency is ENGINE_MAP Renderer #16, **Ready**.
With alpha blending and a draw-order key, this becomes buildable; without them
every sprite is opaque.

**A first-person exploration game with no combat and no UI — a walking
simulator.** **Buildable today, and it is the shape this engine currently fits
best.** FPS camera, character controller, glTF environments, shadowed
directional sun, split-sum IBL, HDR with ACES, bloom, TAA, positioned trigger
volumes for scripted events, and one-shot audio. The two constraints a designer
would feel are the 4-point-light cap and — the one that would actually hurt —
the uncompressed textures (**C1**) bounding how much unique environment art
fits in VRAM.

#### External comparison for C

Against **bgfx**: 89 texture format enumerators, of which ~20 are
block-compressed (BC1–BC7, ETC1/2, EAC, PTC, ATC, ASTC), against Sol's 4 and 0.
That gap is not breadth-for-its-own-sake — block compression is the mechanism
by which a real game's texture set fits in VRAM at all, and its absence is the
concrete ceiling computed in **C1**.

Against **Godot 4**: a comparable feature inventory (forward renderer, PBR,
shadows, IBL, TAA/FSR, bloom) plus the things Sol lacks — text and UI, animation
with skinning, particles, transparency sorting, multiple shadow-casting lights
with cascades. Godot reaches that with orders of magnitude more code; the
relevant comparison is not effort but what a game can use. On the axes Sol has
built, its implementations are recognisably correct (split-sum IBL, Karis
average, YCoCg TAA clipping, Vogel PCF are all current-practice choices, not
approximations).

Where Sol is *ahead* of a typical project at this size: the gate discipline. 67
gates asserting derived values — an analytic camera-aspect delta (`scale=0.9743
expected=0.9743`), VRAM equality across 100 mesh reloads, `mips=12 expected=12`
— is stronger runtime verification than many shipped indie engines carry.

### P — Portability — Solid — B−

Windows-only today; mainstream Linux and macOS are the stated goal.

#### What makes the port easy

The isolation is real and enforced. `check-invariants.ps1` scans 134 source
files for three rule families and passes: D3D12/DXGI/D3DCompiler headers only
in `rhi-d3d12`; `dxcapi` only in `shaders-dxc`; `windows.h`, `wincodec`,
`xaudio2`, `xinput`, `objbase`, `wrl/` only in `platform-win32`, `rhi-d3d12`,
`shaders-dxc`, `audio-xaudio2`, `assets-png-wic`. Five packages hold every
Windows dependency in the engine, and a script proves no sixth appeared.

Consequently the engine-side port is **new packages, not rewrites**:
`rhi-vulkan` (or `rhi-metal`) beside `rhi-d3d12`; `platform-sdl` or
`platform-x11`/`platform-cocoa` beside `platform-win32`; an `audio-*` beside
`audio-xaudio2`; `assets-png-stb` beside `assets-png-wic`; a SPIR-V path beside
the DXIL one. `renderer`, `scene`, `gameplay`, `physics-cpu`, `assets`, `core`,
`math` and `engine` are untouched. That is exactly the payoff the design was
built for, and it is not a claim — the CMake option matrix in CI configures with
each backend off.

#### P1 — The API-neutral header encodes D3D12 concepts — **Medium**

[`packages/rhi/include/engine/rhi/device.hpp:22-30`](../../packages/rhi/include/engine/rhi/device.hpp):

```cpp
// Packed like the D3D12 enums (no graphics API in this header).
// Feature Level 11_0 = 0xB000. Shader Model 6.0 = 0x60.
inline constexpr u32 kGpuFeatureLevel_11_0 = 0xB000;
inline constexpr u32 kGpuShaderModel_6_0 = 0x60;

struct GpuBaseline {
    u32 feature_level = 0;
    u32 shader_model = 0;
};
```

The comment is candid that this mirrors D3D12's numbering, and it is true that
no D3D header is included. But **feature levels are a Direct3D-only concept**.
Vulkan expresses capability as an API version plus extensions plus feature
structs; Metal uses GPU families. A Vulkan backend cannot answer
`feature_level()` truthfully — it must fabricate `0xB000` — and the sandbox's
Ship gate asserts exactly that (`Ship gate: dxc=yes dxil=yes agility=os
sm=6.0 fl=11_0 (pass)`).

This is the audit's own test failing: an interface whose header is clean but
whose *semantics* are one API's. It passed all ten invariants, because the
invariants check includes and not meaning. That is a foreseeable, nameable
failure with nothing covering it — **G3 fires** (capped at B+, not binding
here).

A second, milder instance: `resources.hpp:110` documents
`structured_buffer_count` as "Root SRVs in register space 1, visible to all
stages (t0..tN, space1)" — HLSL register-space vocabulary in the neutral
header. This one happens to port, because DXC's SPIR-V backend maps HLSL
register spaces onto Vulkan descriptor sets, so `space1` → set 1 is the
conventional translation. Worth knowing rather than worth fixing.

#### P2 — The only application does not compile without the Windows backends — **Medium**

`.github/workflows/ci.yml:81-84` states it: "with a backend switched off the
sandbox does not compile (its DXC and PNG includes are unguarded). That is a
real gap, but a separate one." The engine is portable; `packages/sandbox`,
which is also `game.exe` (both built from the same sources via
`engine_add_runtime_app`), is not. Since the sandbox owns every shader and
every pipeline, a Linux port needs the app layer rebuilt regardless — but the
unguarded includes mean it will not even configure-and-compile as a starting
point.

Credit where due: this is *known and written down*, which is what keeps the
dimension in Solid rather than Working.

#### P3 — Resource-state and clip-space conventions are undocumented — **Low**

- `ResourceState` (`resources.hpp:20-29`) is an explicit-barrier model. It maps
  cleanly to Vulkan. On Metal and WebGPU, which do implicit hazard tracking,
  the whole transition machinery becomes no-ops — extra structure to carry, not
  a blocker.
- `Mat4::perspective` and `Mat4::ortho`
  ([`math/src/mat4.cpp:47`, `:77`](../../packages/math/src/mat4.cpp)) bake one
  handedness and depth-range convention, and **no file in the tree states which
  one**. D3D12, Vulkan and Metal all use a [0,1] depth range, so the stated
  targets are fine; a GL-style [-1,1] target would need this changed. The risk
  is low; the absence of a stated convention is the finding, because the next
  person to add a projection helper has nothing to match.
- Shader bytecode is DXIL-only. The `shaders` interface anticipates SPIR-V and
  the backend rejects it with a gate asserting the rejection
  (`RHI contract gate: sampler=yes spirv_rejected=yes target_enum=yes`). The
  seam exists and is honest about being empty.

#### External comparison for P

**bgfx** is the reference for this exact problem and solves the `GpuBaseline`
question differently: it exposes a `Caps` structure of booleans and limits
(`BGFX_CAPS_COMPUTE`, `BGFX_CAPS_TEXTURE_COMPARE_LEQUAL`, per-format support
flags) rather than a version number, precisely so no backend has to lie.
**sokol_gfx** goes further and exposes a small `sg_features` struct. Sol's
feature-level pair is the one place where the abstraction reproduces D3D's
model instead of the union of models — and it is a small, bounded rewrite
(one struct, one gate assertion, a handful of call sites), not a structural
problem.

**The Forge** and **wgpu** both demonstrate the alternative to Sol's
"grow the interface now, implement the second backend later" stance: they
carry all backends simultaneously so the abstraction is continuously
falsified. Sol's approach is the documented deliberate trade
(`.claude/rules/renderer-boundaries.md`: "One production GPU backend until a
second is justified as its own package"), and its cost is exactly what **P1**
found — an untested abstraction accumulates one API's assumptions without
anything noticing.

```
[INFO][general] Content root: C:\Users\mathi\Documents\projects\Sol-Engine-1\build\bin\Debug (install)
```

Not the repo root — the build output directory, layout `install`. The mechanism

`build/bin/Debug/content/shaders/`. The engine has async shader hot-reload

#### D5 — CI structurally cannot run the gates — **Medium, and correctly documented**

- **Prerequisites are specific enough to act on**, including the non-obvious

- **[`tools/check-invariants.ps1`](../../tools/check-invariants.ps1) is the best

- **`.gitattributes` reasons about its exceptions**: `*.bat text eol=crlf`
  because "cmd.exe mis-parses multi-line if/for blocks in an LF-only .bat, which

is more than most projects do.

`debug-draw` is `engine::debug`). It just does not for global state. An agent
applying the rule literally would try to inject the logger through every call
site, or replace the cvar registry, and be wrong to.

#### T3 — Installed skills whose default workflow contradicts this project's — **Medium**

The `SessionStart` hook injects `superpowers:using-superpowers`, which states:
"IF A SKILL APPLIES TO YOUR TASK, YOU DO NOT HAVE A CHOICE. YOU MUST USE IT."
Among the available skills:

- **`superpowers:test-driven-development`** — "Use when implementing any feature
  or bugfix, before writing implementation code." [`CLAUDE.md`](../../CLAUDE.md)
  states: "**There is no test framework.** A gate is a plain function in
  `packages/sandbox/src/main.cpp`."
- **`superpowers:using-git-worktrees`**, **`superpowers:finishing-a-development-branch`**
  ("options for merge, PR, or cleanup") and **`code-review:code-review`**
  ("Code review a pull request") — against a repo whose git workflow is
  "Trunk-based: commit directly to `main`. **No branches, no PRs.**"

The conflict *is* resolvable: `using-superpowers` carries its own priority
ladder putting CLAUDE.md above skills, and CLAUDE.md's gate protocol is TDD in
substance ("Write the gate **before** the implementation and watch it fail
first"). But nothing in the repository states the resolution, so it is
re-derived from first principles every session — which the audit counts as a
defect even when the derivation comes out right.

#### T4 — A mandated loop step that practice abandoned — **Low**

[`CLAUDE.md`](../../CLAUDE.md), "The loop, per Ready row", step 3: "Plan with
`superpowers:writing-plans`, then implement." The tree has **24** design specs
in `docs/superpowers/specs/` and **2** plans in `docs/superpowers/plans/`
(`2026-08-25-claude-code-workflow-migration.md`,
`2026-08-25-foundation-cvars.md`). Step 2 (brainstorming → spec) is followed
consistently; step 3 is not. The documented loop is not the loop being run.

#### What is genuinely good in T

- **The rules files are path-scoped**, so they load where they apply, and the
  scoping decisions carry reasons. `renderer-boundaries.md` deliberately
  includes `packages/sandbox/**` because "the sandbox is where a pass is most
  likely to be added by mistake, and it owns the shaders and pipelines every
  pass needs"; `cpp-conventions.md` includes `CMakeLists.txt` and `cmake/**`
  because the dependency rules apply when editing build files.
- **The renderer-boundaries checklist documents its own failure mode**, which is
  the single most valuable paragraph in the AI surface: "Missing a step fails
  **silently**: every `should_execute` predicate treats a null pipeline as
  'feature disabled', so a forgotten copy line produces a pass that never runs
  and never complains." It then carries a quantified budget note (1 MiB ring,
  1,024 bytes per batch, ~7,000 instances) that matches the code
  (`device_d3d12.cpp:30-42`) exactly.
- **The `SessionStart` hook is carefully written.** It reasons about git
  porcelain XY columns (`'^[MARDU ][MARDU ] '`), deliberately ignores untracked
  files with the reason given — "a stray crash dump or a scratch file is not a
  finished feature, and a nag that is wrong once is a nag that gets ignored
  forever" — and exits 0 on every path so it can never block a session.
- **`ship-feature` refuses to trust a claim**: "**Run it yourself — do not
  accept a claim that it passed.**" It also carries an `allowed-tools`
  allowlist and `disable-model-invocation: true`, so it cannot fire by accident.
- **`analizeMax`'s own claim about CI checks out.**
  [`docs/analysis/README.md`](README.md) asserts the directory is excluded from
  the `doc-links` invariant so a generated file can never turn CI red. Verified:
  `check-invariants.ps1:213-220` excludes `docs/analysis/`, alongside
  `docs/superpowers/` and `reasarch/`, each with a documented reason. The
  self-referential claim is true — which is the opposite of the usual finding
  here.

#### External comparison for T

Compared with the AI-instruction surfaces in public repos that maintain them
seriously (Godot's contribution docs and its `pre-commit` gate; the pattern of
`AGENTS.md`/`CLAUDE.md` files in the Anthropic and OpenAI cookbooks), Sol's is
unusually strong on *structure* — path scoping, a machine-checked invariant
script backing the prose, an explicit gate protocol with a worked example, and
a hook that nudges rather than blocks. It is weaker on *verification of its own
claims*: the invariant script checks doc **links** but nothing checks doc
**assertions**, which is precisely how **T1** and **T2** survived. That is the
one structural improvement available, and it is the same class of tooling the
project has already proven it can build.

## 4. Cross-cutting

Four things appear in more than one dimension.

**1. Nothing verifies that documentation claims match the tree.** The invariant
script checks that markdown *links resolve*; it does not check that markdown
*statements are true*. This single gap produced **T1** (four files vs eight),
**T2** (absolute rule, three exceptions), **D2** (README content root vs
runtime output) and **D3** (stale capacity in a log line). Three of the four are
mechanically checkable — a file count, a grep for globals, a comparison against
a constant. The project has already demonstrated that it builds this kind of
check well.

**2. Capacity constants are the engine's recurring pressure point, and they
move.** `kMaxInstances` 64 → 512 (`5febb3e`), and that single change is what
makes **S2** latent-rather-than-dead, tightens the frame ring from 6 % to 57 %
worst-case occupancy, and left **D3** behind. Meanwhile `kMaxBodies = 256`
(**C4**, the 200-enemy blocker), `kMaxTriggerEvents = 256` (**S3**, silent),
`kMaxPointLights = 4` (**C3**), `kMaxScopes = 8` (**S6**) and
`NameTable::kCapacity` (**S5**) are each a hard array bound with different
overflow behaviour: log-and-degrade, warn-once, silent-drop, or abort. The
inconsistency is the finding, not any single value. No gate reports the frame
ring's high-water mark, so the headroom that makes **S2** latent is currently
unmeasured.

**3. `packages/sandbox/src/main.cpp` is a load-bearing single file.** 5,361
lines holding all 67 gates, all pipelines, all shader paths and the demo. It is
**A3** (architecture), the dominant term in **D1** (2,522 formatter lines), the
reason **P2** exists (unguarded DXC and WIC includes in the only app), and the
reason the pass-adding cost in **A1/T1** is felt as one enormous file plus six
others.

**4. The silent-failure design is deliberate, well-documented, and has exactly
one hole.** `should_execute` treating a null pipeline as "feature disabled" is
a sound design, the rules file warns about it, and all 13 recorders null-check.
Every capacity that was converted degrades *with a log* and has a gate proving
it. Against that consistency, three things stand out precisely because they
break the pattern: **S3** (trigger events drop with no log while siblings warn),
**S2** (one recorder of thirteen fails to stop its caller), and **S1** (the
colour space is wrong with no log, no gate, and no record). The engine's own
standard is what makes these findings sharp.

## 6. Calibration notes

**Distribution.** D+, B, C+, B−, C+, C+. Two of six at B or above. That is not
the leniency pattern the audit warns about (more than half at B+). I re-read the
ceilings against the two Solid grades: A survived G3 on evidence (the layering
is machine-checked across 134 files by a script I ran, not a claim I read), and
P survived it because the port really is additive for eight of ten engine
packages. Neither is resting on documentation.

**Clustering.** Bands are Fragile 1, Working 3, Solid 2. No band holds four or
more, so no central-tendency correction is warranted. The three C+ grades were
derived independently and each names a different single criterion blocking
Solid (no block compression; the formatter trap; two false factual claims). I
checked that they are not the same observation counted three times: they share
only cross-cutting theme 1, and D and T were separable on evidence — D's
formatter and README findings are not instruction defects, and T's rule and
skill-conflict findings are not developer-facing.

**The best argument against my highest grade (A = B).** The layering is proven
only where a script can see it. The ten invariants check `#include` lines and
CMake edges; they cannot see that `RenderSnapshot` is a 13-pointer struct every
new pass must widen, that three copy blocks must be edited by hand, or that
compute is dead weight in the RHI. So "the layering is real" is *verified* for
isolation and *asserted* for evolvability. A reviewer who weighted evolvability
over isolation would grade Architecture at C+, and **A1**'s measured eight-file
cost would be their strongest exhibit — a linear-growth god-struct with no
check protecting it is a maintainability problem that the invariant suite is
structurally blind to. I kept B because the isolation is the harder property to
retrofit and this tree has it genuinely, but the argument is not weak.

**The best argument against my lowest grade (S = D+).** The gamma defect may be
an unrecorded artistic choice rather than an oversight. There is no exposure
control anywhere — light intensities are hand-tuned constants
(`HDR gate: sun=(4.80,4.40,3.80)`) — so if those were tuned by eye against the
author's display, the *final image* may look exactly as intended, and the
"output too dark" half of **S1** would be moot in practice. Only the
input-decode half would remain wrong, which is a quality issue rather than a
Critical one, and S would belong in Working at C or C+ rather than Fragile at
D+. I graded on the tree because I checked and found no such record: `grep -rin
"srgb\|gamma\|colour space\|color space"` across `docs/`, the root markdown
files and `.claude/` returns nothing, and the ROADMAP decision log does record
*why* for shipped work. A single line there stating that sRGB is deliberately
deferred would move this dimension two bands — which is an unusually cheap way
to change a grade, and worth knowing.

**On not manufacturing findings.** Two candidate findings were killed in Pass 4
and are recorded here rather than reported above, because their absence is
itself information: (a) "a scene file can abort the shipping player" — false,
both loaders bound-check and the name table is sized to match exactly (see
**S5**); (b) "a null tonemap pipeline copies an uninitialised transient to the
screen" — the concern was real but every one of the 13 recorders null-checks its
pipeline and its shader reads first, and the app logs pipeline-creation failures
at startup, so the failure is reported before it can be seen.
