## 2. Stability — **B** (Solid)

### What was measured

```
sandbox.exe --gates            → 71 (pass), 0 FAIL, exit 0
ENGINE_GPU_DEBUG=1 …           → D3D12 debug layer: 0 message(s), 0 error(s), 0 warning(s)
game.exe --gates (Release)     → 71 (pass), 0 FAIL, exit 0
```

Release matters here: `ENGINE_ASSERT` has **no `NDEBUG` guard**, so the Release
run exercises all 76 assert sites live.

### The abort-versus-degrade policy is real, not aspirational

This is the strongest thing in the dimension, and it is the one place where a
doc claim and the code agree completely.

`docs/FOUNDATION.md:45` states the rule: asserts "live in **both** Debug and
Release (there is no `NDEBUG` guard), and abort. Reserve them for genuine
programmer error… Capacity that depends on content (arena, frame ring,
descriptor window) returns a failure instead, because aborting there is
unrecoverable *and* untestable: no gate can exercise a path that calls
`std::abort()`."

Checked against the tree, three ways:

- **Frame arena.** `packages/core/src/arena.cpp` — over-capacity returns null
  and logs. Gate output: `Frame arena exhausted: 512 bytes used of 1024, 4096
  more requested. Work is being dropped this frame.`
- **Frame constant ring.** `packages/rhi-d3d12/src/device_d3d12.cpp:1645-1675`
  — `alloc_frame_memory` returns an empty `FrameAllocation{}` when the 1 MiB
  ring is exhausted, logs once per frame, and latches
  `frame_ring_exhausted_frames_`. `begin_frame` clears the latch at
  `device_d3d12.cpp:1277`, so the counter genuinely counts *frames*, not
  occurrences.
- **Content-driven scene overflow.** `packages/scene/src/scene_file.cpp:260`
  and `:276` bound-check `material_count`/`instance_count` **before** calling
  the asserting `add_material`/`add_instance`; `prefab.cpp:70`, `:77`,
  `:128-129` do the same. So a hand-authored scene file cannot reach the
  abort — it is refused instead.

Where the 76 assert sites actually live: 55 in `rhi-d3d12` (null resources,
bound-pipeline preconditions, root-range counts), 12 in `core`, 9 in `scene`,
1 in `renderer`. Every one I traced is an engine-internal precondition, not a
content outcome.

### HRESULT discipline in the D3D12 backend

Per-frame paths check and log:

- `submit()` — `if (FAILED(cmd_list_->Close())) { log_device_error("Command
  list close failed - frame not submitted"); … return; }`
  (`device_d3d12.cpp:1307`). The comment is correct that executing an unclosed
  list is undefined behaviour.
- `present_back_buffer()` — separates `DXGI_ERROR_DEVICE_REMOVED` /
  `DEVICE_RESET` (latch `device_lost_`, log with HRESULT and
  `GetDeviceRemovedReason()`), `DXGI_STATUS_OCCLUDED` (set `occluded_` so an
  unthrottled loop stops burning a core), and other failures
  (`device_d3d12.cpp:2497-2526`).
- `wait_for_gpu()` and `signal_queue()` check `Signal()`.

The unchecked `Close()`/`Reset()` calls I found (`device_d3d12.cpp:1079`,
`1094`, `1251`, `1254`, `1262`) are all on freshly-created or teardown-path
command lists and allocators, where the call cannot meaningfully fail. The
`Create*View` / `SetDescriptorHeaps` / `SetPipelineState` /
`GetCopyableFootprints` calls my first sweep flagged return `void` in the D3D12
API — that candidate finding was withdrawn.

`main()` is the process's one exception boundary
(`packages/sandbox/src/main.cpp:5794-5809`), distinguishing `std::bad_alloc`
and returning exit code 2.

### Findings

**S1 — Four content parsers fail with no diagnostic at all.** *Medium.*

| File | `return false` paths | `log()` calls |
|------|---------------------|---------------|
| `packages/assets/src/cooked.cpp` | 39 | **0** |
| `packages/scene/src/scene_file.cpp` | 22 | **0** |
| `packages/assets/src/pak.cpp` | 21 | **0** |
| `packages/scene/src/prefab.cpp` | 8 | **0** |
| `packages/assets-gltf/src/mesh_loader_gltf.cpp` | 12 | 7 |
| `packages/assets-png-wic/src/image_loader_png.cpp` | 9 | 5 |
| `packages/assets-obj/src/mesh_loader_obj.cpp` | 5 | 3 |
| `packages/core/src/cvar.cpp` | 12 | 6 |

*Failure scenario:* a scene file with 600 instances, or a material index of 20,
or a mistyped float returns bare `false` from `read_world`. The caller learns
nothing — not the line, not the reason, not which of 22 rejection paths fired.
Contrast the rest of the tree, which is meticulous: `cvar.cpp` logs
`Cvar 'gate.text_int' rejected value 'oops' (expected int, line 9)`; the glTF
loader logs `glTF failed validation (cgltf_result 1) — refusing to load`; the
mount check logs `Asset path rejected: escapes its mount root`.

*Why Medium and not High:* nothing outside a gate loads either format today
(see C1), so this is a latent defect in a public API rather than a live silent
failure. It becomes High the day a scene file is loaded from disk.

*No check covers this.* `Scene file gate: … reject=yes` proves rejection
happens; nothing proves a diagnostic is produced.

**S2 — `scene::add_instance` aborts on overflow, and it is a public API.**
*Medium.*

`packages/scene/src/world.cpp:12,20`:
```cpp
ENGINE_ASSERT_MSG(world.material_count < kMaxMaterials, "scene material overflow");
ENGINE_ASSERT_MSG(world.instance_count  < kMaxInstances, "scene instance overflow");
```

*Failure scenario:* a game spawns enemies in a loop and reaches 513. In Release,
the process calls `std::abort()`. FOUNDATION.md reserves asserts for "a
violated precondition **inside the engine**" — a game's spawn loop is outside
it. Every *engine* caller bound-checks first, so the inconsistency is between
the stated rule and one public API's shape, not in current behaviour. Changing
the shape (return `kInvalidInstance`?) is a design decision, so this is on the
Needs-a-decision list, not the plan.

**S3 — One `&&` in the gate sequence lets a failing gate hide the next one.**
*Medium.*

`packages/sandbox/src/main.cpp:5752`:
```cpp
gates_ok = run_graph_gate() && run_swap_gate() && gates_ok;
```

*Failure scenario:* `run_graph_gate()` returns false; `run_swap_gate()` is never
called, so a red run reports one failure when there are two. You fix the graph,
re-run, and only then discover the swap gate was also failing.

The surrounding ~25 call sites all use the pattern that always runs
(`main.cpp:5680-5749`):
```cpp
if (!run_cvar_gate(...)) { gates_ok = false; }
```
so there is exactly one correct answer and it is already established in the
file. This degrades failure diagnosis, which is this project's core method.

**S4 — `RenderGraph::add_pass` does not validate the ref counts it will
iterate.** *Low.*

`RenderPassDesc::kMaxRefs = 4`, with `ResourceRef writes[4]` / `reads[4]` and
caller-set `write_count` / `read_count`. `add_pass`
(`packages/renderer/src/render_graph.cpp:541`) only pushes the desc;
`compile()` then iterates `for (u32 i = 0; i < pass.read_count; ++i)`
(`render_graph.cpp:62`, `:637`). A pass author who sets `read_count = 5`
reads past a fixed array. Highest count actually in use is 3
(`standard_frame.cpp:185`, `:200`). Reachable only from engine code, since the
`no-app-render-passes` invariant forbids app-registered passes.

### External comparison

**Godot 4.x** — device-lost recovery. Sol latches `device_lost_`, logs the
HRESULT and `GetDeviceRemovedReason()`, and stops the loop so shutdown runs
normally (`engine.cpp:311`). It does not recreate the device. Neither does
Godot: handling a driver restart gracefully is an *open proposal*
(godotengine/godot-proposals#10269), which states that today the editor and
most games "freeze or crash" on a driver reset. So on this specific axis Sol's
behaviour — logged, clean shutdown — is at least as good as a shipping
reference engine's, and the difference from Unity/Unreal (which do attempt
recreation) is a real gap rather than an imagined one.

**Where Sol is behind every reference:** there is no sanitizer job, no fuzzing,
and no crash reporter. Unity, Unreal and Godot all run ASan/UBSan or equivalent
in CI. 71 hand-written assertions on one developer's GPU is a narrower net than
any of them, however good the assertions are.

### Genuinely good, credited

- **The mesh-reload VRAM gate.** `Mesh reload gate (100x + 1 MiB dummy): local
  VRAM 29646848 -> 29646848 bytes (pass)`. A hundred load/unload cycles plus a
  deliberate 1 MiB allocation, asserting byte-identical local VRAM. That is a
  leak detector with a number, not a smoke test.
- **The frame-ring *budget* gate.** `batches=512 per_batch=1024
  instances=73728 fixed=3840 worst=601856/1048576 headroom=42.6% (min 15%)
  exhausted=0`. It fails on insufficient *headroom*, not on misbehaviour — a
  budget gate rather than a behaviour gate, which is rare in any codebase.
- **Math NaN guards.** `Mat4::perspective` and `Mat4::ortho` clamp three
  unguarded denominators each, with the reasoning written at
  `packages/math/src/mat4.cpp:48-52`: a degenerate-but-finite frustum is
  visible and local, where inf/NaN "poisons culling and shadow fitting
  silently". Gate: `Math guard gate: zero_fov=finite zero_aspect=finite
  equal_planes=finite zero_extent=finite normal_proj=1.830`.
- **The file logger flushes every line**, because "the record worth keeping is
  the one written immediately before `abort()`", and `assert_fail` writes to
  stderr *and* the log sink before aborting.
- **Mount containment is gated as a security boundary**, not just a
  convenience: `dotdot=blocked absolute=blocked unc=blocked rooted=blocked`.

### The delete test

*If `packages/scene` were deleted:* `engine` and `renderer` keep building —
neither links it (`packages/engine/CMakeLists.txt` lists core, platform, rhi,
renderer, assets, audio, physics). The apps break, and
`packages/sandbox/src/world_extract.cpp` — the scene→snapshot bridge — goes

prose.

*If `packages/rhi-d3d12` were deleted:* `cmake -B build
-DENGINE_RHI_D3D12=OFF` still **configures** (CI proves this on every push),
because `renderer` and `debug-draw` only ever see `rhi`. It does **not** build,
because the sandbox's DXC and PNG includes are unguarded — see P1. So the
interface seam is real and the *app* seam is not.

An abstraction whose seam is regression-tested is not decorative.

### Findings

**A1 — The pass-addition path is eight files, three hand-written copy blocks,
and a documented silent-failure mode.** *Medium.*

`.claude/rules/renderer-boundaries.md` documents it accurately, which is to its
credit and is also the finding: a `I<Thing>Pipeline*` field must be added to
**four** structs in four files — `ForwardDemo` (main.cpp) → `WorldExtractAssets`
(world_extract.hpp) → `ExtractDesc` (renderer/extract.hpp) → `RenderSnapshot`
(renderer/render_snapshot.hpp) — plus the three copy blocks between them, plus
the shader, the `add_pass` registration, the recorder, and the gate.

*Failure scenario, quoting the rule:* "Missing a step fails **silently**: every
`should_execute` predicate treats a null pipeline as 'feature disabled', so a
forgotten copy line produces a pass that never runs and never complains."
Verified in the code — e.g. `render_graph.cpp:363`:
`if (!ctx.snapshot.fxaa_pipeline || ctx.shader_read_count == 0 …) return;`.

This is the single criterion separating this dimension from Exemplary. Fixing
it is a design job (a pipeline registry keyed by name, so the plumbing is one
insertion instead of four), which is why it is on the Needs-a-decision list.

**A2 — `GraphicsPipelineDesc` encodes a D3D12 root-parameter model in a
backend-agnostic header.** *Medium.*

`packages/rhi/include/engine/rhi/resources.hpp` exposes
`constant_buffer_count`, `shader_resource_count`, `structured_buffer_count`,
`sampler_count` — *counts*, not a binding layout — and the comment on
`structured_buffer_count` reads "Root SRVs in register space 1, visible to all
stages (t0..tN, space1)." Register spaces are HLSL/D3D12 vocabulary. A Vulkan
backend must synthesise descriptor sets from counts.

`docs/ARCHITECTURE.md` concedes exactly this ("`set_constant_buffer` /
`set_shader_resource` are a flat per-slot model with no set concept, so a
Vulkan backend must synthesize one"), which moves it from hidden debt to known
debt but does not remove it.

**A3 — Four refs per pass, and compute cannot be a graph pass.** *Low.*

`RenderPassDesc::kMaxRefs = 4` and `enum class PassKind : u8 { Graphics, Copy }`
(`render_graph.hpp:29`). The RHI implements compute — `RHI impl gate:
compute=yes dispatch=yes cubes=yes arrays=yes` — but the graph has no compute
pass kind, so a compute pass cannot participate in graph dependency tracking.
Bloom's downsample/upsample chain is therefore graphics passes over fullscreen
triangles rather than dispatches.

**A4 — `packages/sandbox/src/main.cpp` is 5,811 lines: 26% of the engine and
2.3× the next-largest file.** *Medium.*

| File | Lines |
|------|-------|
| `packages/sandbox/src/main.cpp` | **5,811** |
| `packages/rhi-d3d12/src/device_d3d12.cpp` | 2,566 |
| `packages/physics-cpu/src/physics_cpu.cpp` | 1,421 |
| `packages/renderer/src/render_graph.cpp` | 858 |
| *total, non-vendored* | 22,607 |

It holds all 68 gate functions, every pipeline description, pipeline creation,
the demo world, input handling, and the exception boundary. This is deliberate —
CLAUDE.md defines a gate as "a plain function in
`packages/sandbox/src/main.cpp`" — and it is still the case that the largest
file in the engine is its test harness, and that editing any gate recompiles
all of it. Splitting it is a judgement call; it is on the Needs-a-decision
list.

### External comparison

**bgfx.** Supports Direct3D 11/12, GNM, Metal, OpenGL 2.1/3.1+/ES2/ES3.1,
Vulkan, WebGL 1/2, and WebGPU across Android, iOS, Linux (X11 and Wayland),
macOS, PS4, Raspberry Pi, UWP, Wasm and Windows — and explicitly scopes itself
as a "Bring Your Own Engine/Framework" rendering library with **no** scene
graph, physics, audio, or render graph.

The comparison is instructive in both directions. Sol is *broader*: it has a
render graph with real validation, a scene, physics, audio, and a phased engine
loop — the things bgfx tells you to bring yourself. Sol is *far narrower* in
backends: 1 versus 8 families. And bgfx's abstraction has been proven portable
by eight implementations, where Sol's has been proven by CMake configuring with
one switched off. That difference is a deficiency, not a trade — it is the whole
content of P1.

### Genuinely good, credited

**The `static_assert` family on GPU-facing struct sizes.** This is the thing a
reference implementation could learn from, and I am naming it deliberately:

```
static_assert(sizeof(InstanceData)    == 144);   // render_snapshot.hpp:57
static_assert(sizeof(FrameConstants)  == 336);   // render_snapshot.hpp:90
static_assert(sizeof(ShadowConstants) ==  80);   // render_snapshot.hpp:97
static_assert(sizeof(InstanceBase)    ==  16);   // render_snapshot.hpp:39
static_assert(sizeof(math::Mat4)      ==  64);
static_assert(sizeof(math::Vec4)      ==  16);
static_assert(sizeof(motion::Constants) == 160); // motion.hpp:43
static_assert(sizeof(bloom::Constants)  ==  48); // bloom.hpp:33
static_assert(sizeof(aa::Constants)     ==  16); // aa.hpp:36
```

The failure this prevents is the classic one: a field added to a C++ constant
struct without matching the HLSL mirror, producing a *visual* bug with no
crash, no warning, and no gate that fires. `motion.hpp:28` names the exact
symptom — "motion blur vanishes. No crash, no warning." bgfx and sokol cannot
do this because they do not own shader-side structs; engines that do own them
usually discover the drift by looking at a wrong picture. Turning it into a
compile error is cheap, complete, and unusual.

**The `first_instance` decision, verified against primary sources.**
`ARCHITECTURE.md` explains why a batch's `first_instance` rides in pass
constants rather than in `StartInstanceLocation`: "D3D excludes it from
`SV_InstanceID`, Vulkan folds it into `gl_InstanceIndex`, Metal splits it out
as `[[base_instance]]`." I checked this. It is correct — D3D12's `InstanceID`
counts from 0 regardless of `StartInstanceLocation`, while `gl_InstanceIndex`
starts from `firstInstance`; the discrepancy is tracked as
microsoft/DirectXShaderCompiler#2946 and worked around in Slang via
`SV_StartInstanceLocation`. This is portability foresight in shipped code, made
before a second backend exists, and it is right.

**The render graph validates and says why.** Four negative gates prove it:
missing producer (`Graph: missing producer for 'orphan_color' (ShaderRead) read
by pass 'orphan_read'`), copy-format mismatch (`RGBA8_UNORM -> D32_FLOAT`,
with both format names), cycle (`pass cycle involving 'cycle_a'`), and a
valid-copy control. Every message names the pass.

**One batch list serves shadow, forward and motion**, with the reason recorded:
building it per pass "would let them disagree about grouping, and the motion
pass draws with `DepthTest::Equal`, so geometry that does not rasterize
identically to forward writes nothing and says nothing."

## 4. Capabilities — **C** (Working) · ceiling **G3** fired on C1

### What is actually here, read from the code

**Renderer** — D3D12 forward pipeline, 25 graph passes over 19 resources.
GGX/Cook-Torrance PBR (albedo + packed metal-rough + derivative TBN normal
mapping), one 1024² directional shadow map with 16-tap Vogel PCF, split-sum
IBL (32³ radiance / 16³ irradiance / 32³ prefilter, 5 mips, 128² BRDF LUT),
source-cubemap sky, Karis bloom (5 mips, knee 0.5), ACES tonemap to LDR,
then FXAA | SMAA 1x | TAA (8-sample jitter, YCoCg clipping) — mutually
exclusive, default off. Motion vectors. Instanced draws batched by
pipeline + buffers + textures + index count, one `draw_indexed` and one
constant upload per batch, frustum-culled at extract. PIX markers per pass.
RGBA16F scene colour.

**Shaders** — 18 HLSL files + 2 `.hlsli`, compiled by Windows SDK DXC to
SM 6.0 DXIL on a worker thread, with a disk cache and hot reload.
`Async compile gate: first_poll=0.36ms max_poll=0.42ms slow=0/6`.

**Assets** — glTF 2.0 (all triangle primitives, node-graph walk with world
transforms baked into vertices, normals via the cofactor matrix, mirrored nodes
flip winding, `cgltf_validate` before any unpack), Wavefront OBJ, PNG/JPG/BMP
via WIC with full mip chains, mount-based virtual paths with containment
checks, `SOLC` cooked formats and a `SOLP` pak.

**Scene** — flat instance list, interned names, parent indices, cycle
rejection, world = parent × local, text `solscene` format, prefab
extract/instantiate.

**Physics** — dynamic AABB tree + sequential-impulse solver; AABB, sphere and
Y-up capsule; layers and masks; sensor enter/exit; closest-hit raycasts.

**Gameplay** — kinematic character controller (walk, jump, step, slope, analog
wish) and three game cameras (follow, orbit, FPS).

**Platform** — Win32 window (windowed / borderless / fullscreen, vsync
toggle), keyboard, mouse, XInput gamepads in four slots.

**Runtime** — phased loop (poll → fixed → update → extract → render), cvars
from file and CLI with typed validation, file logger with rotation, CPU
profiler scopes, F3 stats overlay, F4 AABB visualisation, shipping `game.exe`
with identity resources and content beside it.

| Materials | **16** | `scene/world.hpp:13` |

### Findings

**C1 — The scene-file and prefab subsystem is reachable only from gates.**
*High.* **G3 fires: no check covers this, and the gates are what hide it.**

Every caller of the four public entry points is a gate in `main.cpp`:

```
read_world        → main.cpp:1955, 1984, 1985  (run_scene_file_gate)
write_world       → main.cpp:1953, 2042
extract_prefab    → main.cpp:2034, 2039        (run_scene_prefab_gate)
instantiate_prefab→ main.cpp:2045, 2047, 2075
```

*Failure scenario:* a developer reads `docs/ARCHITECTURE.md` — "`scene` … 
`solscene` files, and prefab extract/instantiate" — and tries to ship a game
that loads a level. There is no way to do it. `read_world(std::string_view
text, World& out)` takes text, not a path; no runtime code reads a `.solscene`
file; there is **no `.solscene` file anywhere in the repository**; and the
sandbox builds its 64 instances procedurally
(`for (u32 i = 0; i < kHuskyCount; ++i) add_instance(demo->world, instance)`).
The author must write the file-load, mount-resolve and error-reporting glue
themselves — and S1 means the parser will not tell them why a file was
rejected.

*Adversarial check:* is the map lying? No. ENGINE_MAP defines **Done** as "In
the tree; `--gates` covers it **or** it is the live path", so marking Scene #4
and #5 Done is correct by the project's own definition. The finding is about
the capability, not the bookkeeping.

**C2 — `content.pak` (16.4 MiB) is shipped in the player layout and read by no
runtime path.** *Medium.*

`build/bin/{Debug,Release}/content.pak` is 17,173,162 bytes and is copied next
to both binaries every build (`cmake/EngineRuntimeApp.cmake`) and installed
into the player layout (`packages/game/CMakeLists.txt`). The runtime creates a
**filesystem** loader only (`main.cpp:5657`:
`engine::assets::filesystem::create_asset_loader(*app.filesystem())`);
`create_pak_loader` appears only at `main.cpp:2254` and `:2286`, both inside
`run_pak_gate`. The install also ships the loose `content/` directory, so the
player download carries the 2048² albedo twice.

*Adversarial check, and a partial kill:* `docs/ROADMAP.md:244` records this as
deliberate — Build #5's "**Do not (still):** zip/installer, loading the forward
pass from SOLC." And the shipped pak is not dead: `run_pack_gate` (`main.cpp:2300-2319`)
reads `content.pak` from the executable directory and validates two cooked
entries, so shipping it is what makes the gate meaningful in the player binary.
Downgraded from High to Medium accordingly. The residual is the duplicated
download, which no decision covers.

Also worth recording: the cooker takes a **hard-coded list of five assets**
(`packages/cook/src/main.cpp:130-138` — cube, husky, `albedo.png`,
`Cartoon_Husky_Albedo1.png`, a synthetic beep), not a directory walk. So the
pak is a fixture, not a content pipeline.

### What games this can build

**A 2D platformer — not buildable.** There is no sprite path and no
orthographic 2D pipeline in use; you could fake sprites as textured quads in
the forward pass. The disqualifier is simpler: there is no text rendering, so
you cannot draw a score, a life counter, or a menu. Category 12 (In-game UI)
is *0 done · 0 ready · 11 rows*. **Missing piece: screen-space quads and a text
path (UI #1/#2).**

**A third-person action game with 200 enemies on screen — not buildable**, on
three independent counts. 200 enemies plus weapons and props crosses
`kMaxInstances = 512`; 200 character bodies plus level collision crosses
`kMaxBodies = 256`; and with no skeletal animation the enemies cannot move
their limbs. **Missing piece: skeletal animation — and that one disqualifies
it on its own.**

**A text-heavy RPG — not buildable.** No text rendering, no font pipeline, no
UI, and no save format. **Missing pieces: text (UI #2) and save (Gameplay #9,
itself blocked on Foundation #11 binary primitives).**

**A first-person walkthrough of a static scene under 512 objects — buildable
today.** This is the honest positive answer. You get fly/FPS/follow/orbit
cameras, a character controller with slope and step handling, capsule collision
against a swept AABB tree, raycasts and triggers, PBR with IBL and a shadow and
bloom and TAA, glTF meshes with full mip chains, a 2D one-shot for footsteps,
and a `game.exe` that ships with its content and DLLs beside it and exits 0 on
71 gates. Two caveats that are the dimension in miniature: you author the level
in C++, not in a scene file (C1), and you have no HUD.

### External comparison

**Godot 4.x** has no equivalent of a 512-instance ceiling — its scene tree is
dynamically allocated, and scene files (`.tscn`) are *the* authoring path
rather than a gated library. That contrast is the sharpest statement of C1:
in the reference engine the scene file is how content exists; here it is a
round-trip gate.

**bgfx** would grade higher than Sol on backends and lower on scope: it
deliberately ships no scene, physics or audio at all. Against bgfx, Sol's
capability set is a superset in every area except formats and platforms. That
is a real advantage of the chosen shape, and it does not change the answer to
"what games", because the missing pieces (animation, text) are ones bgfx also
does not provide.

### The conventions that actually do not port, checked

**Depth range — portable.** Working `Mat4::perspective`
(`packages/math/src/mat4.cpp:47-75`) by hand: with `depth_range = near − far`,
`cols[2].z = far/depth_range` and `cols[2].w = −1`, a view-space point at
`z = −near` gives `clip.z/clip.w = 0` and one at `z = −far` gives `1`. That is
the **[0,1]** convention, shared by D3D12, Vulkan and Metal. Only OpenGL's
[−1,1] differs, and OpenGL is not a stated target.

**Shader bytecode — an addition, not a rewrite.** `ShaderTarget::Spirv` is in
the interface and explicitly rejected with a logged error
(`shader_compiler_dxc.cpp:69-73`), gate-proven: `RHI contract gate: sampler=yes
spirv_rejected=yes target_enum=yes`. An honest stub rather than a silent one.

I verified the doc's claim about what the SPIR-V path needs against DXC's own
documentation. `docs/ARCHITECTURE.md` says the path "needs `-spirv` plus the
`-fvk-*-shift` binding shifts, since D3D's separate `b`/`t`/`s` register spaces
all collide at binding 0 in Vulkan. No shader edits." DXC's `docs/SPIR-V.rst`
confirms all of it: `-spirv` is the flag; the default mapping assigns
`:register(xX, spaceY)` to binding `X` in descriptor set `Y` "regardless of the
register type `x`", so two resources of different register type with the same
register number *do* collide; and `-fvk-b-shift` / `-fvk-t-shift` /
`-fvk-s-shift` / `-fvk-u-shift` exist to "apply shifts to all register numbers
of a certain register type". The 18 HLSL files use plain `register(b0)`,
`register(t0..t6)`, `register(s0..s2)` with no explicit `space`, which is
exactly the case the shift flags handle. The doc is right, and the expensive
thing — the shaders — survives.

**Work estimate.** *New packages:* `rhi-vulkan`, `platform-linux` /
`platform-macos`, an `audio-*` backend, an `assets-png-*` replacement for WIC.
*Rewrites:* the sandbox's unguarded backend includes (P1), the pipeline-desc
binding model (P2), and the NDC-Y helpers, which `ARCHITECTURE.md` localises to
`packages/sandbox/content/shaders/common.hlsli`.

### Findings

**P1 — `-DENGINE_RHI_D3D12=OFF` configures but does not build, and only
configure is checked.** *High.* **G3 fires: no compile-time check exists.**

`packages/sandbox/src/main.cpp` includes, with no `#ifdef` guard:
```cpp
#include <engine/assets/png/image_loader_png.hpp>          // line 31
#include <engine/shaders/dxc/shader_compiler_dxc.hpp>      // line 55
#include <engine/shaders/dxc/shader_hot_reload_dxc.hpp>    // line 56
```
and calls `engine::assets::png::load_png_bytes` (4607),
`engine::shaders::dxc::create_hot_reloader` (5372),
`engine::shaders::dxc::create_cached_compiler` (5733).

`cmake/EngineRuntimeApp.cmake` guards the *linking* correctly
(`if (TARGET engine::rhi-d3d12) … ENGINE_HAS_D3D12`), but nothing guards the
*includes*. The CI job's own comment states the consequence: "Configure only:
with a backend switched off the sandbox does not compile (its DXC and PNG
includes are unguarded). That is a real gap."

*Failure scenario:* the first day someone starts `rhi-vulkan`, they cannot get
a clean tree to build against. The `ENGINE_HAS_*` definitions the CMake already
emits are the mechanism; the sandbox simply does not consume them. This is the
one criterion between this dimension and Exemplary.

**P2 — The pipeline description is a D3D12 root-parameter model.** *Medium.*
See A2. `constant_buffer_count` / `shader_resource_count` / `sampler_count` as
counts, plus "Root SRVs in register space 1" in a neutral header. Vulkan must
synthesise descriptor sets; Metal's argument tables map more directly.

**P3 — `ResourceState::ShaderRead` carries no stage scope, and `Format` has
five entries.** *Medium.* `transition()` takes the old state explicitly,
D3D12-style, which works because `RenderGraph` centralises tracking (exactly
one `transition()` escapes it, in a compute gate). But a state that does not
say *which* stage reads forces a Vulkan backend to over-synchronise.
`ARCHITECTURE.md` names both. The five-entry `Format` enum means any second
backend inherits the no-compression ceiling (see C).

**P4 — PNG decode is platform-locked.** *Low.* `assets-png-wic` routes all
image decoding through Windows WIC. macOS and Linux need a new package
(stb_image, libpng, or lodepng). `ARCHITECTURE.md` flags this honestly: the
package is "Named for its backend, not its format… the name is the warning."

**P5 — `d3dcompiler` is linked but never used.** *Low.*
`packages/rhi-d3d12/CMakeLists.txt:8` lists `PRIVATE_DEPS d3d12 dxgi
d3dcompiler`, and no source in the tree includes `d3dcompiler.h` or calls
`D3DCompile*` — the project compiles shaders through DXC (`dxcompiler`). A dead
link dependency on a legacy Windows redistributable, and a small piece of
noise in a portability audit of the link list.

### External comparison

**bgfx** proves the same abstraction across 8 backend families
(D3D11/12, GNM, Metal, OpenGL and ES, Vulkan, WebGL, WebGPU) and 9+ platforms
including Linux under both X11 and Wayland. Sol's `rhi` has one implementation
and its portability evidence is "CMake still configures with it off". The
difference is not stylistic: bgfx has *discovered* the semantic mismatches
(descriptor models, NDC, resource states) by implementing them, while Sol has
*predicted* them in prose. Sol's predictions are unusually accurate — I
verified two of the hardest against primary sources and both held — but a
prediction is not a proof, and P1 means the tree cannot even be compiled in the
configuration a second backend author would start from.

### Genuinely good, credited

- **8 of 142 files, machine-checked.** The `graphics-api-isolation` invariant
  scans every source file on every push. This is the number most engines cannot
  produce about themselves.
- **`ARCHITECTURE.md`'s "Swap cost today" section** is better portability
  analysis than most shipped engines document: SPIR-V binding shifts, NDC Y,
  descriptor sets, barrier stage scopes, and specifically that
  `ISwapchain::present()` returns `void` so "there is no channel for
  `VK_ERROR_OUT_OF_DATE_KHR`. Resize is driven only by window events today,
  which is not sufficient on Wayland." That last sentence is the kind of detail
  that only comes from actually thinking about the target.
- **Two D3D12-isms already removed** rather than left for the second backend's
  author: `IDevice::frame_slot()` (backbuffer index is not a frame-in-flight
  slot on Vulkan) and `ICommandList::set_sampler`.
- **The `first_instance` semantics decision** — see Architecture. Correct
  against three APIs, made before any second backend exists.

**D1 — The tree does not conform to the `.clang-format` it ships, and nothing

## 8. Cross-cutting

**Silent failure is this project's declared enemy and its recurring residual
risk.** It shows up in four dimensions from four directions: the four
undiagnosing parsers (S1), the pass-plumbing path where a missed copy line
disables a feature quietly (A1), one `&&` that hides a second failing gate
(S3), and the shipped-but-unread `content.pak` (C2). The engine's mitigations
where it *has* addressed this are excellent — the `static_assert` family, the
frame-ring log-once, `spirv_rejected`, the four negative graph gates. The
pattern is that silence gets fixed where it has bitten and persists where it has
not yet.

**"Gate-covered" and "reachable" have quietly diverged.** ENGINE_MAP defines
Done as "`--gates` covers it **or** it is the live path", and that *or* is doing
more work than it looks. `read_world`, `write_world`, `extract_prefab`,
`instantiate_prefab` and `create_pak_loader` are all gate-covered and none is
reachable from the runtime. The bookkeeping is honest by its own rules; the
capability picture it produces is not what a reader of ARCHITECTURE.md would
expect. This is C1 and C2, and it is the single most important thing in this
report.

**Documentation is checked where it is countable and drifts where it is
not.** The `roadmap-audit` invariant reconciles LOC figures, `doc-links`
resolves every link, `map-dependencies` walks the backlog as a graph — and
those are all correct. The three doc findings (D3's dependency edge, T1's
enumeration, T4's assert counts) are all in figures and lists that *could* be
checked and are not. The tooling has proved the approach works; it just has not
been pointed at these.

**One file, three concerns, 26% of the tree.** `main.cpp`'s 5,811 lines are the
common factor behind A4, S3 (the one deviant gate-sequence line is buried in
it) and P1 (the unguarded includes are at its top). None of the three is fatal;
all three are the kind of thing that hides in a file that size.

## 10. Calibration notes

**Distribution.** B, B+, C, B, C+, B — **four of six at B or above**, which
trips the leniency check ("more than half at B or above is the documented
symptom of leniency bias"). I re-read the ceilings against the top grades. The
highest grade, A = B+, rests on A1 being Medium rather than High. I re-examined
that: A1's blast radius is a dev-time silent no-op, and the gate protocol
requires a gate per feature, which is its mitigation — so Medium holds, and G3
correctly does not fire on A. The distribution is what it is because three
dimensions (S, A, T) are genuinely well-executed and two (C, D) are not; the
two Working grades are the outliers, and both rest on measured numbers
(109/142 files and 2,883 sites; four gate-only public APIs and a 512-instance
ceiling) rather than on impression.

**Clustering.** Four of six sit in the Solid band (S, A, P, T), which trips the
central-tendency check. I re-derived the two weakest of those. **P = B**: all of
P's soft spots are documented, unusually precisely, and 8-of-142 platform files
is a measured result — but it has one High finding with no compile-time check
and zero second backends, so it does not rise, and I explicitly declined the
B+ that the falsification criterion alone would have supported, because the
"+"'s single missing criterion and G3's cap are the same fact. **T = B**: four
findings, all in enumerations rather than in guidance, against a rules file that
passed eight independent numeric checks — B holds.

**The best argument against my highest grade (A = B+).** A layering whose
primary extension path needs eight files, three hand-written copy blocks, and
carries a documented silent-failure mode is not "top of Solid" — calling it B+
credits the *documentation* of a leaky seam rather than the architecture, and
a reviewer could fairly say the honest grade is B. My counter: the seams that
determine whether this engine can be re-platformed or re-rendered
(renderer↔graphics-API, engine↔scene) are machine-verified clean across 142
files on every push, and the eight-file path is app→renderer plumbing inside one
app, not a boundary violation. I hold B+, and I record that the argument against
it is a good one.

**The best argument against my lowest grade (C = C).** The renderer alone —
a validating render graph, GGX PBR with packed MR and derivative TBN normals,
split-sum IBL, 16-tap Vogel PCF, Karis bloom, Karis TAA, SMAA 1x, motion
vectors, instanced batching, async shader compile with hot reload — is more
capable than plenty of shipped indie engines, and grading the whole dimension C
on the absence of animation and text understates what a graphics programmer
could do here today. My counter: C asks what *games* can be built, and without
text you cannot draw a score. I hold C, and say in prose what the renderer
alone would have earned.

**What I got wrong during this audit, recorded so the next run can trust the
method.** Four candidate findings died in Pass 4 and are not in this report:
(1) "asserts are not compiled out in Release, so all 76 are shipping crashes" —
killed by `FOUNDATION.md:45` documenting the policy *and* the code implementing
it in all three places I checked; (2) "a content scene file can abort the player
via `add_instance`" — killed by `scene_file.cpp:260,276` bound-checking first;
(3) "the D3D12 backend discards HRESULTs" — killed by discovering most of the
flagged calls return `void` in the D3D12 API and the per-frame paths all check;
(4) "`frame_ring_exhausted_frames_` undercounts because the latch is never
reset" — killed by `device_d3d12.cpp:1277`. A fifth was downgraded rather than
killed: C2 went from High to Medium once I found `run_pack_gate` reads the
shipped pak. Two findings were sharpened by adversarial checking rather than
removed: S1 dropped to Medium on reachability, and T4 survived the
"dated-log-entry" defence because the entry is dated today.
