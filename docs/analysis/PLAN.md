### P1 — Guard the one unconditional link to a Windows-only package
- **Files:** `cmake/EngineRuntimeApp.cmake`
- **Why:** Line 30 links `engine::assets-png-wic` inside the unconditional
  `target_link_libraries` block, while the root `CMakeLists.txt` adds
  `packages/assets-png-wic` only inside `if(WIN32)`. The four sibling backends in
  the same function are each guarded with `if(TARGET engine::…)`. On Linux or
  macOS, `cmake -B build` therefore fails at configure, before a single file is
  compiled — step one of the project's stated cross-platform goal.
- **Do:** Remove `engine::assets-png-wic` from the unconditional
  `target_link_libraries` list and add, alongside the four existing guarded
  blocks:
  ```cmake
  if(TARGET engine::assets-png-wic)
      target_link_libraries(${TARGET} PRIVATE engine::assets-png-wic)
  endif()
  ```
  Do **not** add an `ENGINE_HAS_*` compile definition: unlike the four siblings,
  no source file gates on one for PNG, and adding an unused define would be a
  hook with no consumer. Making the sandbox compile without the PNG backend is a
  separate, unbounded change (P2, in Needs a decision).
- **Proof:** On Windows the target exists, so the link is byte-identical:
  `cmake -B build -G "Visual Studio 18 2026" -A x64` configures,
  `cmake --build build --config Debug` is clean, and
  `.\build\bin\Debug\sandbox.exe --gates` still reports

### S1 — Check `Close()` before submitting the copy command list
- **Files:** `packages/rhi-d3d12/src/device_d3d12.cpp`
- **Why:** `end_copy()` (line 1755) discards the HRESULT from
  `copy_list_->Close()` and calls `ExecuteCommandLists` regardless. Submitting a
  command list whose `Close()` failed is undefined and typically removes the
  device. The frame path does check the same call, 450 lines earlier at line
  1307, and the comment above it states that the check "is the difference
  between a logged bad frame and a driver fault". This is a missing guard behind
  an existing pattern: `log_device_error` is already used at eight sites, and it
  latches `device_lost_` only when the device is *actually* removed
  (`device_d3d12.cpp:1360`), so on a live device it logs and nothing else.
- **Do:** In `end_copy()`, capture the `Close()` result. On failure, call
  `log_device_error("Copy command list close failed - copy not submitted")` and
  **skip** `ExecuteCommandLists`, but still call `signal_queue()` and return its
  value — callers at lines 1838 and 1917 wait on the returned fence, and
  returning a stale or unsignalled value would hang them. On success the path is
  unchanged. Then, in `begin_copy()` (line 1749), check the results of
  `copy_allocator_->Reset()` and `copy_list_->Reset()` and log via
  `log_device_error` on failure, matching lines 1281 and 1287 which already do
  exactly this for the frame allocator and list.
- **Proof:** Build clean; `--gates` reports 70 passes and exit 0, unchanged —
  every working path is byte-identical, so no gate output may move. With
  `ENGINE_GPU_DEBUG=1`, the debug layer still reports 0 messages, 0 errors, 0
  warnings, which is what proves no copy was accidentally skipped: the mesh,
  texture and mip-upload gates all run through `end_copy()`, and a dropped copy
  would surface as a wrong readback in `Colour space gate` or
  `RHI impl gate`.

### S2 — Should a pass disabled by a null pipeline say so?
- **Failed:** test 3 — behaviour change (new log output), and test 4 — which
  passes, at what level, and whether once or per-compile are all judgement.
- **The decision:** Sixteen `should_execute` predicates in
  `standard_frame.cpp` treat a null pipeline as "feature disabled" and log

### D3 / S4 — The player build's console window and its only log sink
- **Failed:** test 3 — behaviour change; and the two halves must be decided
  together.
- **The decision:** `game.exe` is a console-subsystem binary
  (`dumpbin`: `3 subsystem (Windows CUI)`), so a console window accompanies the
  shipped game. But `StdoutLogger` writes to `stderr` and nothing else, so that

  row (`ENGINE_MAP.md:58`, Foundation #6) and needs its own decision about
  location — next to the executable, or `%LOCALAPPDATA%`, which the ROADMAP
  currently lists under "Do not (still)". Sequence matters: logger first.
